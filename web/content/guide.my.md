# Agentic Engineer လေ့လာရေးလမ်းညွှန် 2026

နောက်ဆုံးပြင်ဆင်ချက် စက်တင်ဘာ 4, 2026

ရက်သတ္တပတ် (week) 10 ပတ်ကြာ၊ စီမံကိန်းအခြေခံသော ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် (coding agent) များဖြင့် ဆော့ဖ်ဝဲဖန်တီးခြင်း လမ်းညွှန် - ကိုယ်စားလှယ် (agent) များ အတွင်းပိုင်း မည်သို့အလုပ်လုပ်ပုံ၊ နောက်ခံအချက်အလက် ဖန်တီးတည်ဆောက်ခြင်း (context engineering) နှင့် MCP၊ ပြန်လည်အသုံးပြုနိုင်သော ကျွမ်းကျင်မှု (skill) များ၊ ရီပို (repository) အသင့်ဖြစ်မှု၊ AI ကုဒ်ရီဗျူး (code review)၊ လုံခြုံရေး၊ နောက်ကွယ်မှ အလုပ်လုပ်သော ကိုယ်စားလှယ် (background agent) များ၊ အဖွဲ့လိုက် လက်ခံအသုံးပြုမှု (adoption) နှင့် ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ (software factory)။ ရက်သတ္တပတ်တိုင်းတွင် ကန့်သတ်ထားသော အခြေခံကျသော သင်ခန်းစာ (core material) စုစည်းမှုတစ်ခုကို ရေးသားတည်ဆောက်မှုတစ်ခုနှင့် စစ်ဆေးနိုင်သော “ပြီးစီးမှု သတ်မှတ်ချက်များ (done when)” စာရင်းတို့ဖြင့် တွဲဖက်ပေးထားသောကြောင့် သင်သည် စာဖတ်မှတ်တမ်းတစ်ခုအစား အလုပ်လုပ်သော စနစ်တစ်ခုဖြင့် အဆုံးသတ်နိုင်မည်ဖြစ်သည်။

**Credit.** ရက်သတ္တပတ် 10 ပတ် ဖွဲ့စည်းပုံနှင့် အပတ်စဉ် ခေါင်းစဉ်များသည် Stanford ၏ CS146S, *The Modern Software Developer* ([themodernsoftware.dev](https://themodernsoftware.dev/)) ၏ Fall 2026 သင်ရိုးညွှန်းတမ်းကို အခြေခံထားသည်။ ဤလမ်းညွှန်သည် လွတ်လပ်ပြီး အဆိုပါသင်တန်းနှင့် သက်ဆိုင်မှုမရှိပါ။ ဖတ်စရာ၊ ဗီဒီယို၊ ရေးသားတည်ဆောက်မှုနှင့် စစ်ဆေးရန်စာရင်း တစ်ခုစီတိုင်းသည် ကိုယ်ပိုင်ရွေးချယ်မှုသာ ဖြစ်သည်။ လင့်ခ်များအားလုံးကို စက်တင်ဘာ 4, 2026 တွင် စစ်ဆေးခဲ့ပြီး ဗီဒီယိုတိုင်းတွင် ၎င်း၏ ကြာချိန်ပါဝင်သောကြောင့် သင်သည် အချိန် ဘတ်ဂျက် (budget) ကို မှန်ကန်စွာ တွက်ချက်နိုင်သည်။

## ဤလမ်းညွှန်ကို မည်သို့အသုံးပြုမည်နည်း

**တစ်ပတ်လျှင် 10–12 နာရီ** ဖယ်ထားရန် စီစဉ်ပါ။ ၎င်းကို ယခုကဲ့သို့ ခွဲဝေပါ-

- 3–4 နာရီ: ထိုရက်သတ္တပတ် (week) အတွက် **အခြေခံကျသော သင်ခန်းစာ (Core material)**။ ရက်သတ္တပတ်တစ်ခုစီ၏ core စာရင်းကို လေးနာရီဝန်းကျင်တွင် ကန့်သတ်ထားပြီး ကြာမြင့်ချိန်များကို အကြောင်းအရာတစ်ခုစီ၏ ဘေးတွင် ရေးသားထားသည်။
- 5–6 နာရီ: အပတ်စဉ် **အကောင်အထည်ဖော် ရေးသားခြင်း (Build)**။
- 1–2 နာရီ: ရလဒ်များ၊ မအောင်မြင်မှုများ၊ ကုန်ကျစရိတ် (cost) များနှင့် ရရှိခဲ့သော သင်ခန်းစာများကို မှတ်တမ်းတင်ပြီး ထိုရက်သတ္တပတ်၏ **ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)** စာရင်းကို အမှန်ခြစ်ပါ။

**ပိုမိုနက်ရှိုင်းသော သင်ခန်းစာ (Deeper material)**၊ **မဖြစ်မနေကြည့်ရှုရန် မလိုသော ဗီဒီယိုလမ်းကြောင်း** နှင့် **ကိရိယာများ နှင့် ကိုးကားချက်များ** အောက်ရှိ အရာအားလုံးသည် ရွေးချယ်နိုင်သော (optional) များ ဖြစ်ကြသည်။ စိတ်ပါဝင်စားမှုအပေါ် မူတည်၍ ရွေးချယ်ပါ၊ အကုန်လုံးပြီးအောင် လုပ်ရန် မကြိုးစားပါနှင့်။

ဆယ်ပတ်လုံးလုံးတွင် အလတ်စား ရီပို (repository) တစ်ခုကို အသုံးပြုပါ။ UI၊ စမ်းသပ်မှုများ (tests) နှင့် CI ပါဝင်သော လတ်ဆတ်သည့် SaaS အက်ပ်၊ ဒေဗလော့ပါ ကိရိယာ (tool) သို့မဟုတ် API တစ်ခုသည် သီးခြားစီဖြစ်နေသော ကစားစရာ စီမံကိန်း ဆယ်ခုထက် ပိုမိုထိရောက်သည်။ ရက်သတ္တပတ်တိုင်းတွင် ထိုစနစ်တစ်ခုတည်းကိုပင် ပိုမိုကောင်းမွန်အောင် ပြုလုပ်သင့်သည်။

အတောင့်တင်းဆုံး အခမဲ့ အခြေခံသင်ခန်းစာမှာ Hugging Face ၏ [Context Course](https://huggingface.co/learn/context-course/en/unit0/introduction) (သင်ခန်းစာများ- Agent Skills, MCP, Plugins, Sub-agents, Hooks နှင့် Bonus ဖြစ်သော Nano Harness) ဖြစ်သည်။ ၎င်းသည် ဤလမ်းညွှန်၏ ပထမဝက်နှင့် ပုံမှန်မဟုတ်ဘဲ အလွန်ပင် ကိုက်ညီမှုရှိသည်။ ပိုမိုနက်ရှိုင်းစေရန်နှင့် တိုးချဲ့ရန် အောက်ပါ သင်ခန်းစာများကို အသုံးပြုပါ။

ဤလမ်းညွှန်သည် မည်သည့် ပရိုဂရမ်းမင်းဘာသာစကားအပေါ်မျှ အခြေမခံပါ၊ ဥပမာအများစုသည် Python သို့မဟုတ် JavaScript ကို အသုံးပြုထားသည်။ သင့်အနေဖြင့် ခိုင်မာသော ပရိုဂရမ်းမင်း အတွေ့အကြုံ (တက္ကသိုလ်အဆင့် သင်တန်း နှစ်ခု သို့မဟုတ် သုံးခု သို့မဟုတ် ၎င်းနှင့် ညီမျှသော အတွေ့အကြုံ) ရှိရန် လိုအပ်သည်။ စက်သင်ယူခြင်း (machine learning) နောက်ခံရှိပါက ပိုမိုအထောက်အကူပြုသော်လည်း မဖြစ်မနေ လိုအပ်သည်တော့ မဟုတ်ပါ၊ အကယ်၍ transformers များကို သင် မရင်းနှီးသေးပါက Week 1 optional foundation တွင် ၎င်းလိုအပ်ချက်ကို ဖြည့်ဆည်းပေးထားသည်။

### ကိရိယာအသုံးပြုမှု နှင့် ဘတ်ဂျက်

အချို့သော ကိရိယာများသည် စာရင်းသွင်းမှု သို့မဟုတ် API key တစ်ခု လိုအပ်သည်။ Week 1 မစတင်မီ ဤအချက်ကို ဆုံးဖြတ်ပါ-

- **ပင်မ ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် (coding agent) တစ်ခုကို ရွေးချယ်ပါ** ပြီးလျှင် Week 3–4 ရှိ ပုဂ္ဂိုလ်ရေးဆိုင်ရာ ပြင်ဆင်ဖန်တီးမှု အလုပ်များသည် ပိုမို ထိရောက်ပေါင်းစည်းသွားစေရန် အနည်းဆုံး ငါးပတ်ခန့် ထိုတစ်ခုတည်းကိုပဲ ဆက်လက်အသုံးပြုပါ။ သင့်တော်သော ရွေးချယ်မှုများ- [Claude Code](https://code.claude.com/docs/en/common-workflows) (စာရင်းသွင်းမှု သို့မဟုတ် API key)၊ [OpenAI Codex CLI](https://github.com/openai/codex) (open source၊ စာရင်းသွင်းမှု သို့မဟုတ် API key)၊ [Cursor](https://cursor.com/docs/cloud-agent)၊ [Gemini CLI](https://github.com/google-gemini/gemini-cli) (open source၊ အခမဲ့သုံးနိုင်သော အဆင့်ပါဝင်သည်) သို့မဟုတ် [opencode](https://github.com/sst/opencode) (open source၊ သင့်ကိုယ်ပိုင် key ယူဆောင်လာပါ)။
- **မစတင်မီ လစဉ် ကုန်ကျစရိတ် သတ်မှတ်ချက်ကို အသေအချာ သတ်မှတ်ပါ** ပြီးလျှင် သင့် build မှတ်စုများနှင့်အတူ တစ်ပတ်စီ၏ ကုန်ကျစရိတ်ကို မှတ်တမ်းတင်ပါ။ ဤလမ်းညွှန်တွင် ကုန်ကျစရိတ်သည် နောက်မှ စဉ်းစားရမည့်အရာ မဟုတ်ဘဲ ပထမဦးစားပေး တိုင်းတာရမည့် အချက် ဖြစ်သည်။
- **[prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) ကို လေ့လာပါ** ပြီးလျှင် လက်အောက်ခံ ကိုယ်စားလှယ် (subagent) များနှင့် စစ်ဆေးခြင်းလုပ်ငန်းစဉ်များအတွက် ပိုမိုဈေးသက်သာသော မော်ဒယ် (model) ကို အသုံးပြုပါ။ ထိန်းမနိုင်သိမ်းမရ ဖြစ်သွားသော ကုန်ကျစရိတ် အများစုသည် လုပ်ငန်းစဉ်စက်ဝန်း တိုင်းတွင် နောက်ခံအချက်အလက် (context) အရှည်ကြီးများကို ထပ်ခါထပ်ခါ ပြန်လည်ပေးပို့ခြင်းမှ လာခြင်းဖြစ်သည်။
- **အခမဲ့ လမ်းကြောင်း-** Hugging Face သင်တန်းများ၊ အထက်ပါ အခမဲ့သုံးနိုင်သော အဆင့်များပါသည့် open-source ကိုယ်စားလှယ် (agent) များ နှင့် ဤလမ်းညွှန်ပါ ဆောင်းပါးတိုင်းသည် ကုန်ကျစရိတ် မရှိပါ။ သင့် builds အတွက် အသုံးပြုသည့် API အသုံးပြုမှုတစ်ခုတည်းသာ ငွေကုန်ကျမည် ဖြစ်သည်။

## ရက်သတ္တပတ် 10 ပတ်ကို ခြုံငုံကြည့်ရှုခြင်း

| ရက်သတ္တပတ် | အကြောင်းအရာ | သင် တည်ဆောက်ရမည့်အရာ |
|---|---|---|
| 1 | ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် (coding agent) များ၏ အတွင်းပိုင်းများ | ကိရိယာ (tool) 4 ခုနှင့် အပြည့်အစုံ လော့ဂ် မှတ်တမ်းတင်ခြင်း (logging) ပါဝင်သော လိုင်း 300–500 ရှိ terminal ကိုယ်စားလှယ် (agent) တစ်ခု |
| 2 | အဆင့်မြင့် နောက်ခံအချက်အလက် ဖန်တီးတည်ဆောက်ခြင်း (context engineering) | စာမျက်နှာတစ်မျက်နှာပါ စပက် (spec) တစ်ခု၊ RePPIT မှတစ်ဆင့် ဖြန့်ချိလိုက်သော လုပ်ဆောင်ချက်တစ်ခုနှင့် ကိရိယာ 2–4 ခု ပါဝင်သော MCP server တစ်ခု |
| 3 | ကိုယ်စားလှယ် ကျွမ်းကျင်မှု (skill) များနှင့် CLI | အထောက်အကူပြု script တစ်ခုပါဝင်သော ထုပ်ပိုးထားသည့် ကျွမ်းကျင်မှုတစ်ခု၊ ထို့အပြင် browser မှ မောင်းနှင်သော web ကျွမ်းကျင်မှုတစ်ခု |
| 4 | သင့်ကိုယ်စားလှယ်နှင့် ရီပို (repository) အား စိတ်ကြိုက်ပြင်ဆင်ခြင်း | ရီပို လမ်းညွှန်ချက်များ၊ ဟွတ် (hook) 2 ခု၊ နှင့် အစီအစဉ်ဆွဲသူ (planner) / အကောင်အထည်ဖော် ရေးသားသူ (implementer) / စစ်ဆေးသူ (reviewer) အဖြစ် ခွဲခြားမှု |
| 5 | ကိုယ်စားလှယ်အတွက် အသင့်ဖြစ်မှု (agent-ready) ရှိသော ကုဒ်အစုအဝေး (codebase) များ | အမှတ်ပေးထားသော အသင့်ဖြစ်မှု စစ်ဆေးခြင်းနှင့် အသစ်ဖြစ်သော ကိုယ်စားလှယ်တစ်ခုကို ကုန်ထုတ်စွမ်းအား (productivity) မြင့်မားစေသည့် ပြုပြင်မှုများ |
| 6 | ကိုယ်စားလှယ်မှ လုပ်ဆောင်သော ကုဒ်ရီဗျူး (code review) | ပူးလ်ရီကွက်စ် (pull request) များနှင့် ချိတ်ဆက်ထားပြီး PR 5 ခုပေါ်တွင် တိုင်းတာထားသော၊ ပြင်းထန်မှုအဆင့်အလိုက် စီစဉ်ထားသည့် ရီဗျူး စံသတ်မှတ်ချက် |
| 7 | လုံခြုံရေး | ခြိမ်းခြောက်မှုပုံစံ (threat model) တစ်ခု၊ CI အတွင်းရှိ SAST / SCA / လျှို့ဝှက်ချက် (secret) စကန်ဖတ်မှုများ၊ နှင့် ပရွမ့်ထဲသို့ အန္တရာယ်ရှိကုဒ်ထည့်သွင်းခြင်း (prompt injection) စမ်းသပ်မှုတစ်ခု |
| 8 | နောက်ကွယ်မှ အလုပ်လုပ်သော ကိုယ်စားလှယ် (background agent) များ | သီးခြားခွဲထားမှု၊ ဘတ်ဂျက် (budget) များ၊ မှတ်တိုင် (checkpoint) များနှင့် ထပ်မံကြိုးစားခြင်း (retry) များ ပါဝင်သော အစ်ရှူး (issue) မှ PR သို့ လုပ်ငန်းစဉ် |
| 9 | AI-native အဖွဲ့တစ်ခု တည်ဆောက်ခြင်း | မော်ဒယ် (model) ဝင်ပေါက် (gateway) တစ်ခု၊ MCP ဗဟိုဝင်ပေါက် (portal) တစ်ခု၊ နှင့် စာမျက်နှာတစ်မျက်နှာပါ လက်ခံအသုံးပြုမှု (adoption) မူဝါဒတစ်ခု |
| 10 | ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ (software factory) နှင့် အနာဂတ် | အကဲဖြတ်ခြင်း (eval) အစုအဝေးတစ်ခုနှင့် ထိန်းချုပ်ထားသော တိုးတက်မှု လုပ်ငန်းစဉ်စက်ဝန်း တစ်ခုပါဝင်သည့် ခြေရာခံ မှတ်တမ်းတင်ထားသော (traced) အစမှအဆုံး စက်ရုံတစ်ခု |

## ရက်သတ္တပတ် 1 — ကုဒ်ရေးပေးသော ကိုယ်စားလှယ်များ (Coding Agents) ၏ အတွင်းပိုင်း လည်ပတ်ပုံ

**အဓိကထားမည့်အရာ:** LLM ၏ အစစ်အမှန် သဘောတရားနှင့် အကူကိရိယာများ နောက်ကွယ်ရှိ ကိုယ်စားလှယ် လုပ်ငန်းစဉ်စက်ဝန်း (agent loop) ၏ လုပ်ဆောင်ပုံ၊ အခြေခံ ကိရိယာ (tool) အစုအဝေး (read, write, edit, bash) နှင့် ၎င်းတို့မှတစ်ဆင့် အလုပ်များ လည်ပတ်သွားပုံ၊ ထုတ်လုပ်မှုအဆင့် ကုဒ်ရေးပေးသော ကိုယ်စားလှယ်များက ၎င်းတို့၏ စနစ် ပရွမ့် (system prompt) များ နှင့် ကိရိယာ သတ်မှတ်ချက် (tool definition) များကို တည်ဆောက်ပုံ။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 h 20 min)

1. **ဗီဒီယို:** Andrej Karpathy, [Intro to Large Language Models](https://www.youtube.com/watch?v=zjkBMFhNj_g) (59 min) — အကောင်းဆုံး ကျစ်လျစ်သော အယူအဆအခြေခံ။ အချိန်ရပါက ပိုမိုပြည့်စုံသော အခြေခံရရှိရန် ၎င်း၏ ပိုရှည်သော [Deep Dive into LLMs like ChatGPT](https://www.youtube.com/watch?v=7xTGNNLPyMI) (3 h 31 min) ကို အစားထိုး ကြည့်ပါ။
2. **ဆောင်းပါး + ကုဒ်:** Thorsten Ball, [How to Build an Agent](https://ampcode.com/notes/how-to-build-an-agent) (ကုဒ်နှင့်အတူ ≈ 60 min) — မရှိမဖြစ် ကိရိယာ လုပ်ငန်းစဉ် စက်ဝန်းပါဝင်သည့် သေးငယ်၍ ဖတ်ရှုနားလည်လွယ်သော ကုဒ်ရေးပေးသော ကိုယ်စားလှယ်။ ဤရက်သတ္တပတ်၏ ရေးသားတည်ဆောက်မှုအတွက် နမူနာအဖြစ် အသုံးပြုပါ။
3. **ဆောင်းပါး:** Anthropic, [Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents) (25 min) — လုပ်ငန်းစဉ် (workflow) များ နှင့် ကိုယ်စားလှယ်များ အကြောင်း၊ မြှင့်တင်ထားသော LLM လုပ်ငန်းစဉ် စက်ဝန်းအကြောင်း စံပြဆောင်းပါး။ အောက်ပါ Barry Zhang ၏ ဟောပြောချက်သည် ၎င်း၏ ဗီဒီယိုပုံစံ ဖြစ်သည်။
4. **အင်ဂျင်နီယာဆိုင်ရာ ဆောင်းပါး:** OpenAI, [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/) (20 min) — ကိုယ်စားလှယ် လုပ်ငန်းစဉ်စက်ဝန်း နှင့် ၎င်း၏ ဒီဇိုင်းဆိုင်ရာ အပေးအယူများကို ထုတ်လုပ်မှုအဆင့် ပုံစံဖြင့် ရှင်းလင်းထားချက်။
5. **ဟောပြောချက်:** Anthropic မှ Barry Zhang, [How We Build Effective Agents](https://ai.engineer/talks/effective-ai-agents) (15 min) — ကိုယ်စားလှယ်တစ်ဦး၏ ကန့်သတ်ထားသော နောက်ခံအချက်အလက် (context) အတွင်းမှ အနည်းဆုံး လုပ်ငန်းစဉ်စက်ဝန်း၊ ကိရိယာကို ခေါ်ယူအသုံးပြုခြင်း (tool call)၊ ဆုံးရှုံးနိုင်ခြေ၊ စမ်းသပ်ခြင်း (test) နှင့် စစ်ဆေးပြင်ဆင်ခြင်း။

### ထုတ်လုပ်မှုအဆင့် ပရွမ့်များနှင့် ကိရိယာ သတ်မှတ်ချက်များ

အကျဉ်းချုပ်များကို မဟုတ်ဘဲ အစစ်အမှန် စနစ် ပရွမ့်များကို ဖတ်ပါ။ ဤအရာများသည် အများပြည်သူကြည့်ရှုနိုင်ပြီး ဖတ်ရှုနိုင်ပါသည်:

- OpenAI Codex CLI သည် open source ဖြစ်သည်။ `gpt_5_codex_prompt.md`၊ `gpt_5_2_prompt.md` နှင့် အလားတူ အမည်ရှိသော ဖိုင်များပါရှိသည့် [codex-rs/core](https://github.com/openai/codex/tree/main/codex-rs/core) မှ မော်ဒယ် (model) ပရွမ့်များ (prompt) နှင့် `codex-rs/prompts/templates/compact/` အောက်ရှိ အချက်အလက် ကျစ်လျစ်အောင်ပြုလုပ်ခြင်း (compaction) ပရွမ့်ကို ဖတ်ပါ။
- Google ၏ [Gemini CLI](https://github.com/google-gemini/gemini-cli) သည် ၎င်း၏ စနစ် ပရွမ့်ကို `packages/core/src/core/prompts.ts` တွင်လည်းကောင်း၊ ၎င်း၏ MCP ပရွမ့်များကို `packages/core/src/prompts/` တွင်လည်းကောင်း သိမ်းဆည်းထားသည်။
- [opencode](https://github.com/sst/opencode) သည် တတိယမြောက် open-source ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် ဖြစ်ပြီး ၎င်း၏ ပရွမ့်များနှင့် ကိရိယာ ပုံစံသတ်မှတ်ချက်များကို အထက်ပါ နှစ်ခုနှင့် နှိုင်းယှဉ်ကြည့်နိုင်သည်။
- **ဗီဒီယို:** [How Claude Code Works](https://ai.engineer/talks/how-claude-code-works) (1 h 06 min) — ပရွမ့်အခြေခံ ဗိသုကာပုံစံ၊ ကိရိယာကို ခေါ်ယူအသုံးပြုခြင်း၊ လက်အောက်ခံ ကိုယ်စားလှယ် (subagent) များ၊ ခွင့်ပြုချက် (permission) များ နှင့် အကဲဖြတ်ခြင်း (evaluation) နေ့စဉ်သုံး လုပ်ငန်းစဉ်များအကြောင်း သီးခြား အလုပ်ရုံဆွေးနွေးပွဲ။ ထုတ်လုပ်မှုအဆင့် ကိုယ်စားလှယ်တစ်ဦး၏ ပရွမ့်နှင့် ကိရိယာ ဒီဇိုင်းအကြောင်း အကောင်းဆုံး အများပြည်သူဆိုင်ရာ ရှင်းလင်းချက်။

- OpenHands မှ Robert Brennan, [Software Development Agents: What Works and What Doesn't](https://ai.engineer/talks/software-development-agents-what-works-and-what-doesn-t) (17 မိနစ်) — အယ်ဒီတာ၊ တာမီနယ်၊ ဘရောက်ဆာ၊ ဆန်းဘောက်စ် (sandbox) နှင့် လုပ်ဆောင်ချက် စက်ဝန်း။

### တည်ဆောက်ခြင်း

စာကြောင်းရေ 300–500 ခန့်ဖြင့် တာမီနယ် ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် (coding agent) တစ်ခုကို တည်ဆောက်ပါ။ ၎င်းကို ကိရိယာလေးခု ပေးပါ- ဖိုင်များကို စာရင်းပြရန်၊ ဖိုင်တစ်ခုကို ဖတ်ရန်၊ ဖိုင်တစ်ခုကို ပြင်ဆင်ရန်နှင့် shell command တစ်ခုကို အလုပ်လုပ်စေရန်။ မော်ဒယ်၏ တုံ့ပြန်မှု၊ ကိရိယာကို ခေါ်ယူအသုံးပြုခြင်း (tool call)၊ ရလဒ်၊ တိုကင် (token) အရေအတွက်နှင့် ရပ်တန့်မည့် အခြေအနေတိုင်းကို လော့ဂ် မှတ်တမ်းတင်ခြင်း (logging) ပြုလုပ်ပါ။ ၎င်းကို သေးငယ်သော ရီပို (repository) လုပ်ငန်းဆောင်တာ သုံးခုတွင် စမ်းသပ်ခြင်း (test) ပြုလုပ်ပြီး၊ ကျရှုံးမှုတိုင်းကို မော်ဒယ်၊ နောက်ခံအချက်အလက် (context)၊ ကိရိယာ သို့မဟုတ် ထိန်းချုပ်မှု-စက်ဝန်း ကျရှုံးမှုအဖြစ် လူကိုယ်တိုင် ခွဲခြားသတ်မှတ်ပါ။

ထို့နောက် ထုတ်လုပ်မှုသုံး စနစ် ပရွမ့် (system prompt) တစ်ခု (Codex သို့မဟုတ် Gemini CLI) ကို အစမှအဆုံးဖတ်ပြီး မှတ်ချက်ရေးပါ- မည်သည့် စာကြောင်းများက သရုပ်သဘာဝကို သတ်မှတ်သည်၊ မည်သည့်အရာများက ဘေးကင်းလုံခြုံရေး နယ်နိမိတ်များကို သတ်မှတ်သည်၊ မည်သည့်အရာများက ကိရိယာ ရွေးချယ်မှုကို ပုံဖော်သည်၊ မည်သည့်အရာများက ရပ်တန့်ခြင်းကို ကိုင်တွယ်ဖြေရှင်းသည် စသည်တို့ဖြစ်သည်။ ၎င်းကို သင့်ကိုယ်ပိုင် ပရွမ့် (prompt) နှင့် နှိုင်းယှဉ်ပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- သင်၏ ကိုယ်စားလှယ် (agent) သည် လုပ်ငန်းစဉ် 3 ခုအနက် အနည်းဆုံး 1 ခုကို ကိရိယာ (tool) 4 ခုစလုံး အသုံးပြု၍ အစမှအဆုံး ပြီးမြောက်ရမည်။
- အလုပ်လုပ်သည့် အကြိမ်တိုင်းတွင် အလှည့်အလိုက် တိုကင် (token) အရေအတွက်များနှင့် နောက်ဆုံး ရပ်တန့်ရသည့် အကြောင်းရင်းပါဝင်သော လော့ဂ် မှတ်တမ်း (log) တစ်ခု ရှိရမည်။
- အနည်းဆုံး အတန်း 5 တန်းပါရှိသော ကျရှုံးမှုဇယားတစ်ခု ရှိရမည်ဖြစ်ပြီး၊ အတန်းတစ်ခုစီကို မော်ဒယ် (model)၊ နောက်ခံအချက်အလက် (context)၊ ကိရိယာ သို့မဟုတ် ထိန်းချုပ်မှု လုပ်ငန်းစဉ်စက်ဝန်း အဖြစ် အမျိုးအစားခွဲခြားထားရမည်။
- အနည်းဆုံး မှတ်ချက် 10 ခုပါဝင်သော အမှန်တကယ်အသုံးပြုမည့် ပရွမ့် (prompt) 1 ခုကို သင်၏မှတ်စုများထဲသို့ ထည့်သွင်းထားရမည်။

## ရက်သတ္တပတ် 2 — နောက်ခံအချက်အလက် ဖန်တီးတည်ဆောက်ခြင်း (Advanced Context Engineering)

**အဓိကထားမည့်အချက်:** အဆင့်မြင့် ပရွမ့် ဖန်တီးတည်ဆောက်ခြင်း (prompting techniques) နည်းလမ်းများ နှင့် တစ်ခုချင်းစီကို မည်သည့်အချိန်တွင် အသုံးပြုရမည်၊ RePPIT (လေ့လာစူးစမ်းခြင်း (Research)၊ အဆိုပြုခြင်း (Propose)၊ အစီအစဉ် (Plan)၊ အကောင်အထည်ဖော် ရေးသားခြင်း (Implement)၊ စမ်းသပ်ခြင်း (Test)) နှင့် သတ်မှတ်ချက်အခြေခံ ဆော့ဖ်ဝဲရေးသားခြင်း (spec-driven development)၊ MCP အခြေခံများ (servers၊ clients၊ ကိရိယာများ (tools)၊ transport)၊ ကိုယ်စားလှယ် (agent) များ အသုံးပြုရလွယ်ကူစေရန် ကိရိယာ သတ်မှတ်ချက် (tool definition) များကို ဒီဇိုင်းထုတ်ခြင်း။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 မိနစ် 50 မိနစ်)

1. **ဗီဒီယို/ပေါ့ဒ်ကတ်စ်:** Dex Horthy နှင့် The Pragmatic Engineer၊ [Context Engineering](https://youtu.be/Usufn8IQJgw) (1 မိနစ် 33 မိနစ်) — နောက်ခံအချက်အလက် (context)၊ ထိန်းချုပ်စမ်းသပ်စနစ် (harnesses) များ၊ ကိုယ်စားလှယ် လုပ်ငန်းစဉ်စက်ဝန်း (loops) များ၊ လေ့လာစူးစမ်းခြင်း/အစီအစဉ်/အကောင်အထည်ဖော် ရေးသားခြင်း လုပ်ငန်းစဉ် (workflows) များ၊ အချက်အလက် ကျစ်လျစ်အောင်ပြုလုပ်ခြင်း (compaction) နှင့် ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ (software factories) များအကြောင်း။ [article and transcript](https://newsletter.pragmaticengineer.com/p/context-engineering-with-dex-horthy) သည် မှတ်စုထုတ်ရန်အတွက် အသုံးဝင်သည်။
2. **ဆောင်းပါး:** Anthropic၊ [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) (25 မိနစ်) — နောက်ခံအချက်အလက်ကို အကန့်အသတ်ရှိသော အရင်းအမြစ်တစ်ခုအဖြစ် ပုံဖော်ထားသည့် အဓိက မူဘောင်- စနစ် ပရွမ့် (system prompts) များ၊ ကိရိယာများ၊ နမူနာများ၊ ရယူသုံးစွဲခြင်း (retrieval) နှင့် အချက်အလက် ကျစ်လျစ်အောင်ပြုလုပ်ခြင်း။
3. **ဗီဒီယို:** Anthropic၊ [Prompting for Agents](https://www.youtube.com/watch?v=XSZP9GhhuAc) (29 မိနစ်) — မော်ဒယ် (model) သည် ကိရိယာများနှင့်အတူ ကိုယ်စားလှယ် လုပ်ငန်းစဉ်စက်ဝန်းအတွင်း လည်ပတ်သည့်အခါ ပရွမ့် ဖန်တီးတည်ဆောက်ခြင်း ပြောင်းလဲသွားပုံ။
4. **ဆောင်းပါး:** Anthropic၊ [Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents) (25 မိနစ်) — ကိရိယာ အမည်များ၊ ဖော်ပြချက်များ၊ နယ်နိမိတ်များ၊ ရလဒ်များ နှင့် အကဲဖြတ်ခြင်း (evaluation)။
5. **သတ်မှတ်ချက်:** Model Context Protocol၊ [Specification](https://modelcontextprotocol.io/specification/latest) (architecture၊ transports နှင့် tools အပိုင်းများအတွက် 30 မိနစ်) — မည်သည့် သင်ခန်းစာကိုမျှ မလေ့လာမီ ပင်မရင်းမြစ်ကို ဖတ်ရှုပါ။
6. **အသေးစိတ်ရှင်းလင်းချက်:** GitHub၊ [Spec Kit](https://github.github.com/spec-kit/) နှင့် ၎င်း၏ [Agentic SDD workflow](https://github.github.com/spec-kit/reference/agentic-sdd.html) (20 မိနစ်) — သတ်မှတ်ချက်အခြေခံ ဆော့ဖ်ဝဲရေးသားခြင်း၏ အခိုင်အမာ အကောင်အထည်ဖော်မှုတစ်ခု။

- **လေ့လာစူးစမ်းခြင်း (research)၊ အစီအစဉ် (plan)၊ အကောင်အထည်ဖော် ရေးသားခြင်း (implement):** Dex Horthy, [No Vibes Allowed: Solving Hard Problems in Complex Codebases](https://ai.engineer/talks/context-engineering-for-complex-codebases) (21 min) — ပစ်မှတ်ထား လေ့လာစူးစမ်းခြင်း၊ သေချာရည်ရွယ်၍ အချက်အလက် ကျစ်လျစ်အောင်ပြုလုပ်ခြင်း (compaction)၊ ခိုင်မာသော အစီအစဉ်များ၊ နှင့် လူကိုယ်တိုင် စစ်ဆေးခြင်း။
- **ရေရှည်အတွက် နောက်ခံအချက်အလက် (context):** LangChain မှ Harrison Chase, [Context Engineering Our Way to Long-Horizon Agents](https://www.youtube.com/watch?v=vtugjs2chdA) (39 min)။
- **သတ်မှတ်ချက်အခြေခံ ဆော့ဖ်ဝဲရေးသားခြင်း (spec-driven development):** Amazon Kiro မှ Al Harris, [Spec-Driven Development: Agentic Coding at FAANG Scale and Quality](https://ai.engineer/talks/spec-driven-development-agentic-coding-at-faang-scale-and-quality-al-harris-amazon-kiro) (1 h 04 min) — လိုအပ်ချက်များ၊ လက်ခံနိုင်သော စံသတ်မှတ်ချက်များ (acceptance criteria)၊ ဒီဇိုင်းဆိုင်ရာ မှတ်တမ်းဖိုင်များ၊ လုပ်ဆောင်ရန်အချက်များ နှင့် လမ်းညွှန်စာရွက်စာတမ်းများ။
- **MCP အလုပ်ရုံဆွေးနွေးပွဲ:** Anthropic မှ Mahesh Murag, [Building Agents with Model Context Protocol](https://www.youtube.com/watch?v=kQmXtrmQ5Zg) (1 h 44 min) — ပရိုတိုကော ဖန်တီးသူများထံမှ အပြည့်အစုံ အလုပ်ရုံဆွေးနွေးပွဲ။
- **MCP ဗီဒီယို သင်တန်း:** DeepLearning.AI နှင့် Anthropic, [MCP: Build Rich-Context AI Apps](https://www.deeplearning.ai/courses/mcp-build-rich-context-ai-apps-with-anthropic) (≈ 1 h 30 min) — ဗိသုကာပုံစံ၊ ဆာဗာများ၊ ကလိုင်းယင့်များ၊ ကိရိယာ (tool) များ၊ ရင်းမြစ်များ၊ ပရွမ့်များ၊ အဝေးမှ လွှင့်တင်ခြင်း နှင့် Inspector-အခြေခံ စမ်းသပ်ခြင်း (test)။
- **ဗိသုကာပုံစံ အမြန်လေ့လာခြင်း:** Gaurav Sen, [Model Context Protocol: A Deep Dive](https://www.youtube.com/watch?v=uBL0siiliGo) (9 min)။

### တည်ဆောက်ခြင်း

သင့် ရီပို (repository) အတွက် အမှန်တကယ် လုပ်ဆောင်ချက် 1 ခုကို ရွေးချယ်ပါ။ ရည်ရွယ်ချက်၊ ကန့်သတ်ချက်များ၊ အကျုံးမဝင်သောအရာများ၊ လက်ခံနိုင်မှု စစ်ဆေးချက်များ၊ ရှားပါးသော ချွင်းချက်အခြေအနေ (edge case) များ နှင့် စမ်းသပ်မှု အစီအစဉ် 1 ခု ပါဝင်သော 1 မျက်နှာစာ စပက် (spec) ကို ရေးသားပါ။ အဆင့်တစ်ခုကိုမျှ မကျော်ဘဲ လေ့လာစူးစမ်းခြင်း (research) → အဆိုပြုခြင်း → အစီအစဉ် (plan) ဆွဲခြင်း → အကောင်အထည်ဖော် ရေးသားခြင်း (implement) → စမ်းသပ်ခြင်း (test) ကို လိုက်နာပါ၊ ထို့နောက် အဆင့်တစ်ခုစီမှ ထွက်ပေါ်လာသော မှတ်တမ်းဖိုင်ကို သိမ်းဆည်းထားပါ။

ထို့နောက် သီးသန့် ကိရိယာ (tool) 2 ခုမှ 4 ခုအထိ ပါဝင်သော MCP server 1 ခုကို တည်ဆောက်ပါ။ ၎င်းကို MCP Inspector တွင် ဦးစွာ စမ်းသပ်ပါ၊ ထို့နောက် သင်၏ ကိုယ်စားလှယ် (agent) မှတစ်ဆင့် စမ်းသပ်ပါ။ အဆင်ပြေချောမွေ့သော လမ်းကြောင်းများ၊ မှားယွင်းနေသော ကန့်သတ်ဘောင်များ၊ ကြီးမားသော ရလဒ်များ၊ အချိန်ကုန်ဆုံးမှုများ နှင့် ခွင့်ပြုချက် (permission) ကျရှုံးမှုများကို စမ်းသပ်ပါ။ အသစ်စက်စက် ကိုယ်စားလှယ်က မှန်ကန်သော ကိရိယာကို ပုံမှန်ရွေးချယ်ပြီး မှန်ကန်သော ကန့်သတ်ဘောင်များ ထည့်သွင်းပေးသည်အထိ ဖော်ပြချက်တစ်ခုစီကို ပြင်ဆင်မွမ်းမံပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- စပက် (spec) ရှိနေရမည် ဖြစ်ပြီး RePPIT အဆင့်တစ်ခုစီမှ သိမ်းဆည်းထားသော အချက်အလက်သိုလှောင်မှုတစ်ခု (လေ့လာစူးစမ်းခြင်း (research) မှတ်စုများ၊ အဆိုပြုချက်၊ အစီအစဉ် (plan)၊ diff၊ စမ်းသပ်ခြင်း (test) ရလဒ်များ) ကို ထုတ်လုပ်ပေးပြီး ဖြစ်ရမည်။
- MCP server သည် တရားဝင်သော Input နှင့် မတရားဝင်သော Input များပါဝင်သည့် ကိရိယာ (tool) တိုင်းကို လွှမ်းခြုံထားသော Inspector ဆက်ရှင်ကို အောင်မြင်စွာ ဖြတ်သန်းရမည်။
- လတ်ဆတ်သော ကိုယ်စားလှယ် (agent) တစ်ခုသည် ရေးသားပြင်ဆင်ထားသော တောင်းဆိုချက် 5 ခုအနက် 5 ခုလုံးတွင် မှန်ကန်သော ကိရိယာကို ခေါ်ယူအသုံးပြုခြင်း (tool call) ပြုလုပ်ရမည်။
- လုပ်ဆောင်ချက်အတွက် ကုန်ကျစရိတ် (cost) နှင့် တိုကင် (token) အရေအတွက်များကို သင်၏ မှတ်စုများတွင် မှတ်တမ်းတင်ထားရမည်။

## ရက်သတ္တပတ် 3 — ကိုယ်စားလှယ် ကျွမ်းကျင်မှုများ (agent skills) နှင့် CLI

**Focus:** ကျွမ်းကျင်မှု (skill) ဆိုသည်မှာ အဘယ်နည်း၊ `SKILL.md` နှင့် Script များသည် လုပ်ငန်းစဉ် (workflow) တစ်ခုကို မည်သို့ သင်္ကေတပြု ပုံဖော်ပေးသနည်း၊ ဝဘ်ဆိုင်ရာ ကျွမ်းကျင်မှုများနှင့် ကိုယ်စားလှယ်၏ စွမ်းဆောင်ရည်ကို ကုဒ်အစုအဝေး (repository) ပြင်ပသို့ တိုးချဲ့ခြင်း၊ CLI မှတစ်ဆင့် ထိရောက်စွာ အလုပ်လုပ်ခြင်း။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 h 40 min)

1. **Course unit:** Hugging Face၊ [Agent Skills](https://huggingface.co/learn/context-course/en/unit1/introduction) (≈ 60 min) — အခြားနေရာသို့ ပြောင်းရွှေ့အသုံးပြုနိုင်ပြီး လိုအပ်သလို အဆင့်ဆင့် ဖော်ထုတ်ပြသပေးသော ကျွမ်းကျင်မှုများအကြောင်း အကောင်းဆုံး စနစ်တကျ မိတ်ဆက်ထားသော သင်ခန်းစာ။
2. **Article:** Anthropic၊ [Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) (20 min)၊ လက်တွေ့ အလုပ်လုပ်ထားသော နမူနာများအဖြစ် အများပြည်သူသုံး [skills repository](https://github.com/anthropics/skills) နှင့်အတူ။
3. **Specification + tutorial:** [Agent Skills Quickstart](https://agentskills.io/skill-creation/quickstart) (30 min)။
4. **Video:** Cursor မှ Lee Robinson၊ [The Beginner's Guide to Coding with Cursor](https://www.youtube.com/watch?v=Gqpk7-FruqI) (45 min) — Type သတ်မှတ်ထားသော ဘာသာစကားများ၊ လင့် (lint) ပြုလုပ်ခြင်း၊ ဖော်မတ်ပြင်ခြင်း၊ စမ်းသပ်ခြင်း (test) များ၊ ဘရန့်ချ် စစ်ဆေးခြင်း (branch review) နှင့် ပြိုင်တူ နောက်ကွယ်မှ အလုပ်လုပ်ခြင်း။
5. **CLI foundation:** MIT၊ [The Missing Semester 2026: Course Overview and Introduction to the Shell](https://missing.csail.mit.edu/2026/course-shell/) (လေ့ကျင့်ခန်းများနှင့်ဆိုလျှင် ≈ 60 min) — Shell သွားလာအသုံးပြုခြင်း၊ ပေါင်းစပ်ဖွဲ့စည်းခြင်း၊ Script ရေးသားခြင်း၊ Stream များ၊ ခွင့်ပြုချက် (permission) များ နှင့် ဘေးကင်းလုံခြုံသော Bash အလေ့အကျင့်များ။
6. **Standard:** [AGENTS.md](https://agents.md/) (10 min) — နမူနာများနှင့် သဘောတူညီချက်များကို ယခု ဖတ်ရှုပါ၊ ရီပို (repository) ဆိုင်ရာ ညွှန်ကြားချက်များသည် Week 4 တွင် အဓိက အကြောင်းအရာ ဖြစ်လာပါမည်။

### ကိရိယာများနှင့် ကိုးကားချက်များ

- [Command Line Interface Guidelines](https://clig.dev/) — ကိုယ်စားလှယ်များ (နှင့် လူများ) စိတ်ချယုံကြည်စွာ မောင်းနှင်နိုင်သော CLI များကို မည်သို့ ဒီဇိုင်းထုတ်ရမည်နည်း။ ၎င်းကို သင်၏ ကျွမ်းကျင်မှုဆိုင်ရာ ကူညီပေးသည့် Script တွင် အသုံးချပါ။
- ဝဘ်ဆိုင်ရာ ကျွမ်းကျင်မှု ကိရိယာများ: [Playwright MCP](https://github.com/microsoft/playwright-mcp)၊ [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) နှင့် [browser-use](https://github.com/browser-use/browser-use)။
- Claude Code၊ [Common workflows](https://code.claude.com/docs/en/common-workflows) — Git အလုပ်လမ်းကြောင်း (git worktrees) များ၊ ပြိုင်တူ အလုပ်လုပ်သည့် Session များ နှင့် CLI မှတစ်ဆင့် စကားဝိုင်းများကို ပြန်လည်စတင်ခြင်း။

### ထပ်ဆောင်း ဗီဒီယို သင်ခန်းစာများ

- **Hands-on skills workshop:** Supabase မှ Pedro Rodrigues၊ [Skill Issue: How We Used AI to Make Agents Actually Good at Supabase](https://ai.engineer/talks/skill-issue-how-we-used-ai-to-make-agents-actually-good-at-supabase) (1 h 19 min) — `SKILL.md`၊ ပံ့ပိုးပေးသော Script များ၊ လိုအပ်သလို အဆင့်ဆင့် ဖော်ထုတ်ပြသခြင်း နှင့် လမ်းကြောင်းသတ်မှတ်ပေးခြင်း (routing) အပြုအမူများကို တည်ဆောက်ပြီး အကဲဖြတ်ခြင်း (eval)။
- **Web skills:** Browserbase မှ Paul Klein၊ [Bringing Agents onto the World Wide Web](https://ai.engineer/talks/bringing-agents-onto-the-world-wide-web) (18 min) — Browser-agent ထိန်းချုပ်စမ်းသပ်စနစ် (harness) များ၊ ကွန်ရက်ကြားဖြတ်ဖမ်းယူခြင်း၊ WebMCP၊ Playwright CLI၊ မှတ်ဉာဏ် နှင့် ပြန်လည်အသုံးပြုနိုင်သော ဝဘ်ဆိုက် ကျွမ်းကျင်မှုများ။
- **Concept explainer:** Greg Isenberg၊ [How AI agents & Claude skills work (Clearly Explained)](https://www.youtube.com/watch?v=S_oN3vlzpMw) (35 min)။
- **Long form:** Lex Fridman နှင့် Cursor အဖွဲ့၊ [Future of Programming with AI](https://www.youtube.com/watch?v=oFfVt3S51T4) (2 h 29 min) — Editor ဒီဇိုင်း၊ ခန့်မှန်းပြင်ဆင်မှုများ (speculative edits) နှင့် Cursor ပူးတွဲတည်ထောင်သူများ ကိုယ်စားလှယ်များအကြောင်း တွေးတောပုံ။

### တည်ဆောက်ခြင်း

သင် အနည်းဆုံး သုံးကြိမ်ပြုလုပ်ခဲ့သော လုပ်ငန်းစဉ် (workflow) တစ်ခုကို ရှာပါ- release notes၊ database migration checks၊ API endpoint scaffolding၊ dependency upgrades သို့မဟုတ် UI ယခင်အလုပ်လုပ်ပြီးသားများ ပြန်လည်ချို့ယွင်းမှု စစ်ဆေးခြင်းများ (UI regression checks)။ ၎င်းကို ကျွမ်းကျင်မှု (skill) တစ်ခုအဖြစ် အောက်ပါတို့နှင့်အတူ ထုပ်ပိုးပါ-

- မော်ဒယ်/ကိုယ်စားလှယ်ကို မည်သည့်အချိန်တွင် အသုံးပြုရမည်ကို ပြောပြသည့် တိုတောင်းသော `SKILL.md` တစ်ခု။
- အဆင့်ဆင့် အချက်အလက်ဖော်ပြခြင်း (Progressive disclosure)- ရှားပါးသော အသေးစိတ်အချက်အလက်များကို ချိတ်ဆက်ထားသော ရည်ညွှန်းချက်များတွင် ထားရှိပါ။
- အထက်ပါ CLI လမ်းညွှန်ချက်များကို လိုက်နာသော ရလဒ်သေချာသော စစ်ဆေးမှု (deterministic check) အကူအညီပေးရေး စခရင်ပတ်တစ် ခု။
- စမ်းသပ်ရန် သတ်မှတ်ချက် သို့မဟုတ် နမူနာ ထည့်သွင်းချက် တစ်ခု။
- အောင်မြင်/ကျရှုံး စစ်ဆေးသည့် စိစစ်ရေး ကွန်မန်း တစ်ခု။

၎င်းကို သီးသန့် အသစ်ဖြစ်သော ကိုယ်စားလှယ် အလုပ်လုပ်ချိန် (agent session) မှ ထည့်သွင်းချက် နှစ်ခုပေါ်တွင် စေခိုင်းပါ။ ညွှန်ကြားချက်များ အဓိပ္ပာယ် မရှင်းလင်းသော သို့မဟုတ် နောက်ခံအချက်အလက် လက်ခံနိုင်စွမ်း (context window) ပေါ် ဝန်ပိသွားသော နေရာများကို မှတ်တမ်းတင်ပါ။ ထို့နောက် ဝဘ် ကျွမ်းကျင်မှု တစ်ခု ထည့်သွင်းပါ- သင်၏ အလုပ်လုပ်နေသော အက်ပ်တွင် တစ်ခုခုကို စိစစ်ပေးသည့် ဘရောက်ဆာအခြေပြု စစ်ဆေးမှု (Playwright MCP သို့မဟုတ် Chrome DevTools MCP) တစ်ခု။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- ကျွမ်းကျင်မှုသည် အပို ထပ်ဆောင်း သင်ကြားပေးရန် မလိုဘဲ သီးသန့် အသစ်ဖြစ်သော အလုပ်လုပ်ချိန်မှ ထည့်သွင်းချက် နှစ်ခုပေါ်တွင် မှန်ကန်စွာ အလုပ်လုပ်သည်။
- အကူအညီပေးရေး စခရင်ပတ်တွင် မှတ်တမ်းတင်ထားသော ထွက်ရှိမှု ကုဒ် ရှိပြီး ဆယ်စက္ကန့်အောက် ဖြင့် အလုပ်လုပ်သည်။
- ဝဘ် ကျွမ်းကျင်မှုသည် စစ်မှန်သော ဘရောက်ဆာကို မောင်းနှင်ပြီး သင်၏ အက်ပ်ပေါ်တွင် အောင်မြင်/ကျရှုံး ရလဒ်ကို အစီရင်ခံသည်။
- သင်၏ မှတ်စုများတွင် `SKILL.md` ၌ ပြင်ဆင်ခဲ့သော မရှင်းလင်းမှု တိုင်းနှင့် အကြောင်းရင်းကို စာရင်းပြုစုထားသည်။

## ရက်သတ္တပတ် 4 — သင်၏ ကိုယ်စားလှယ် (agent) နှင့် ရီပို (repository) အား စိတ်ကြိုက်ပြင်ဆင်ခြင်း

**အဓိကထားရမည့်အရာ:** `CLAUDE.md` နှင့် `AGENTS.md`၊ မည်သည့်အရာကို မည်သည့်နေရာတွင် ထားရမည်၊ လင့် (lint) ဂိတ်များ၊ စမ်းသပ်ခြင်း (test) လုပ်ဆောင်မှုများနှင့် ဘေးကင်းလုံခြုံရေး ထိန်းကွပ်ချက် (guardrail) များအတွက် ဟွတ် (hook) များ၊ လက်အောက်ခံ ကိုယ်စားလှယ် (subagent) ပုံစံများ (အစီအစဉ်ဆွဲသူ / အကောင်အထည်ဖော် ရေးသားသူ / စစ်ဆေးသူ (reviewer))။

### တည်ဆောက်ခြင်း

ကျစ်လျစ်သော ရီပို (repository) ညွှန်ကြားချက်ဖိုင်တစ်ခု ထည့်သွင်းပါ။ ၎င်းကို စွယ်စုံကျမ်းတစ်ခုကဲ့သို့မဟုတ်ဘဲ မြေပုံတစ်ခုကဲ့သို့ သဘောထားပါ - စနစ်တည်ဆောက်ပုံဆိုင်ရာ ဝင်ပေါက်များ၊ အမိန့်ပေးချက်များ၊ သဘောတူညီချက်များ၊ ဘေးကင်းလုံခြုံရေး နယ်နိမိတ်များနှင့် ပိုမိုနက်ရှိုင်းသော စာရွက်စာတမ်းများသို့ လင့်ခ်များ။ မြန်ဆန်သော လင့် (lint) သို့မဟုတ် စမ်းသပ်မှု တံခါးကို မောင်းနှင်သည့် ရလဒ်သေချာသော စစ်ဆေးမှု (deterministic check) ဟွတ်တစ်ခုနှင့် အန္တရာယ်ရှိသော အမိန့်ပေးချက်ကို တားဆီးသည့် ဟွတ်တစ်ခု ထည့်သွင်းပါ။

အခန်းကဏ္ဍ သုံးခု (အစီအစဉ်ရေးဆွဲသူ၊ အကောင်အထည်ဖော် ရေးသားသူ နှင့် သီးခြားလွတ်လပ်သော စစ်ဆေးသူ) ဖန်တီးပြီး တစ်ခုချင်းစီကို တိကျကျဉ်းမြောင်းသော သဘောတူညီချက် ပေးပါ။ တူညီသော ဖန်တီးမှုလုပ်ဆောင်ချက် (feature) ကို ကိုယ်စားလှယ် တစ်ခုတည်းဖြင့် တစ်ကြိမ်၊ အခန်းကဏ္ဍ သုံးခုပါ လုပ်ငန်းစဉ် (workflow) ဖြင့် တစ်ကြိမ် လုပ်ဆောင်ပါ။ ကုန်ဆုံးသွားသော အချိန်၊ တိုကင် (token) များ၊ တွေ့ရှိရသော ချို့ယွင်းချက်များနှင့် လူကိုယ်တိုင် ဝင်ရောက်လုပ်ဆောင်ရမှု ပမာဏတို့ကို နှိုင်းယှဉ်ပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- လမ်းညွှန်ချက်ဖိုင်သည် စာကြောင်း 150 အောက်ဖြစ်ပြီး သီးသန့် ကိုယ်စားလှယ် (agent) အသစ်တစ်ခုသည် ၎င်းမှတစ်ဆင့် setup၊ စမ်းသပ်မှုများ (tests) နှင့် လင့် (lint) တို့ကို ယင်းတစ်ခုတည်းဖြင့် လုပ်ဆောင်နိုင်သည်။
- လင့်/စမ်းသပ်မှု ဟွတ် (hook) သည် တမင်တကာ ပျက်စီးအောင်လုပ်ထားသော ကော်မစ် (commit) ကို တားဆီးပေးပြီး၊ ဘေးကင်းရေး ဟွတ်သည် တမင်တကာ အန္တရာယ်ရှိအောင် လုပ်ထားသော ကိန်းဂဏန်းညွှန်ကြားချက်ကို တားဆီးပေးသည်။
- တစ်ခုတည်းသော ကိုယ်စားလှယ် နှင့် အခန်းကဏ္ဍ သုံးခုပါဝင်သော နှိုင်းယှဉ်ချက်ဇယားတွင် အချိန်၊ တိုကင်များ (tokens)၊ ချို့ယွင်းချက်များနှင့် ဝင်ရောက်စွက်ဖက်မှုများ ပါဝင်သည်။
- လက်အောက်ခံ ကိုယ်စားလှယ် (subagent) ခွဲထုတ်မှုသည် စိစစ်တွက်ချက်ထားသော ကိန်းဂဏန်းများကို ကိုးကား၍ ၎င်းအတွက် ကုန်ကျစရိတ် ကာမိခြင်း ရှိ၊ မရှိကို စာပိုဒ်တစ်ပိုဒ် ရေးသားခဲ့သည်။

## ရက်သတ္တပတ် 5 — ကိုယ်စားလှယ်အတွက် အသင့်ဖြစ်မှု (agent-ready) ရှိသော ကုဒ်အစုအဝေး (codebase) များ

**အဓိကထားလေ့လာရန်-** ရီပို (repository) တစ်ခုကို ကိုယ်စားလှယ်အတွက် အသင့်ဖြစ်မှု ရှိစေသောအရာများ- တည်ဆောက်ပုံ၊ စာရွက်စာတမ်းများ၊ စမ်းသပ်ခြင်း (test) များနှင့် စစ်ဆေးမှုများ၊ အသင့်ဖြစ်မှုကို အမှတ်ပေးခြင်းနှင့် စစ်ဆေးခြင်း၊ လက်တွေ့ ရီပိုများတွင် ကိုယ်စားလှယ် (agent) များကို အဟန့်အတားဖြစ်စေသော အဖြစ်များသည့် လိုအပ်ချက်များ။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 နာရီ 30 မိနစ်)

1. **အင်ဂျင်နီယာပိုင်းဆိုင်ရာ လေ့လာမှု-** OpenAI၊ [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/) (30 မိနစ်) — ဤရက်သတ္တပတ်အတွက် အရေးအကြီးဆုံး ဖတ်ရှုရန်စာဖြစ်နိုင်သည်- ရီပို ရှင်းလင်းပြတ်သားမှု၊ စနစ်တကျရေးသားထားသော စာရွက်စာတမ်းများ၊ စက်ဖြင့်ထိန်းကွပ်ထားသော ပြောင်းလဲမှုမရှိသည့်အရာများနှင့် အဆင့်လိုက် ဖော်ပြခြင်း။
2. **လက်တွေ့လမ်းညွှန်-** Adobe၊ [Repository Harnesses for AI Coding Agents](https://opensource.adobe.com/ai-repo-harness-guide/00-Introduction/) (≈ 60 မိနစ်) — ရီပိုတစ်ခုကို ကိုယ်စားလှယ်များမှ သွားလာကြည့်ရှုနိုင်ပြီး စစ်ဆေးအတည်ပြုနိုင်ရန် ပြုလုပ်နည်းအတွက် အခမဲ့၊ စနစ်ကျသော လမ်းညွှန်။
3. **အက်ဆေး-** Martin Fowler၊ [Harness Engineering](https://martinfowler.com/articles/harness-engineering.html) (20 မိနစ်)။
4. **ဗီဒီယိုများ-** Factory မှ Eno Reyes၊ [Making Codebases Agent-Ready](https://ai.engineer/talks/making-codebases-agent-ready) (16 မိနစ်) နှင့် [Building Reliable Agentic Systems](https://ai.engineer/talks/building-reliable-agentic-systems) (18 မိနစ်) — စက်ပိုင်းဆိုင်ရာ စစ်ဆေးအတည်ပြုခြင်း၊ လင့် (lint) လုပ်သော ကိရိယာများ၊ အစမှအဆုံး စမ်းသပ်မှုများ၊ ကြားခံချိတ်ဆက်မှု စာရွက်စာတမ်းများ၊ အစီအစဉ် (plan) ရေးဆွဲခြင်း၊ အခြေပြုချိတ်ဆက်ခြင်းနှင့် လူကိုယ်တိုင် ကြီးကြပ်ကွပ်ကဲမှု။
5. **Evals အခြေခံ-** Hamel Husain၊ [Your AI Product Needs Evals](https://hamel.dev/blog/posts/evals/) (20 မိနစ်) — အကဲဖြတ်ခြင်း (evaluation / eval) အလေ့အကျင့်ကို ဤနေရာမှ စတင်ပါ၊ ရက်သတ္တပတ် 10 သည် ၎င်းအပေါ်တွင် မူတည်နေသည်။
6. **အသင့်ဖြစ်မှုကို တိုင်းတာခြင်း-** Sourcegraph မှ Beyang Liu၊ [The ROI of AI: Why You Need Eval Frameworks](https://ai.engineer/talks/the-roi-of-ai-why-you-need-eval-frameworks) (25 မိနစ်) — တိကျခိုင်မာသော အကဲဖြတ်မှုများ၊ ရီပို နောက်ခံအချက်အလက် (context)၊ အင်ဂျင်နီယာပိုင်းဆိုင်ရာ KPI များနှင့် အလုပ်တွင်ကျယ်ဟန်ဆောင်ခြင်းကို ရှောင်ရှားခြင်း။

### ပိုမိုနက်ရှိုင်းသော သင်ခန်းစာ

- OpenAI၊ [Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/)။
- Dex Horthy ၏ [Context Engineering](https://youtu.be/Usufn8IQJgw) အင်တာဗျူးကို ပြန်လည်လေ့လာပါ၊ အထူးသဖြင့် ထိန်းချုပ်စမ်းသပ်စနစ် (harness)၊ ကိုယ်စားလှယ် လုပ်ငန်းစဉ်စက်ဝန်း (agent loop) နှင့် ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ (software factory) အခန်းများ။
- [Diátaxis](https://diataxis.fr/) — ကိုယ်စားလှယ်များ ကောင်းစွာ သွားလာကြည့်ရှုနိုင်သော စာရွက်စာတမ်း ဖွဲ့စည်းပုံ (သင်ခန်းစာများ၊ ပြုလုပ်နည်းများ၊ ကိုးကားချက်၊ ရှင်းလင်းချက်)။
- Chroma၊ [Context Rot](https://research.trychroma.com/context-rot) — သေသပ်ကျစ်လျစ်ပြီး အညွှန်းကောင်းစွာတပ်ထားသော ရီပိုတစ်ခုသည် အရာအားလုံးကို နောက်ခံအချက်အလက်ထဲသို့ စုပုံထည့်လိုက်ခြင်းထက် အဘယ်ကြောင့် ပိုကောင်းသနည်း။

### ထပ်ဆောင်း ဗီဒီယို သင်ခန်းစာများ

- **စမ်းသပ်မှုများကို ထိန်းချုပ်စမ်းသပ်စနစ်အဖြစ် အသုံးပြုခြင်း-** The Pragmatic Engineer ဖြင့် Kent Beck၊ [TDD, AI agents and coding](https://www.youtube.com/watch?v=aSXaxOdVtAQ) (1 နာရီ 15 မိနစ်) — ကိုယ်စားလှယ်များမှ ကုဒ်ရေးသောအခါ test-driven development သည် အဘယ်ကြောင့် အထူးစွမ်းရည်တစ်ခု ဖြစ်လာသနည်း။
- **ထိန်းချုပ်စမ်းသပ်စနစ် ဒီဇိုင်း-** LangChain မှ Harrison Chase၊ [When to Build Your Own Agent Harness](https://www.youtube.com/watch?v=HI2q3ci3Iuc) (23 မိနစ်)။

### တည်ဆောက်ခြင်း

သင်၏ ရီပိုကို ရှုထောင့်ငါးခုဖြင့် စစ်ဆေးပါ- ရှာဖွေတွေ့ရှိနိုင်စွမ်း၊ တပ်ဆင်သတ်မှတ်ခြင်း၊ တုံ့ပြန်မှုအမြန်နှုန်း၊ တည်ဆောက်ပုံကို လိုက်နာစေခြင်းနှင့် ချို့ယွင်းမှုမှ ပြန်လည်ရယူခြင်း။ တစ်ခုစီကို အထောက်အထားစာများဖြင့် 1 မှ 5 အထိ အမှတ်ပေးပါ။ အသစ် clone လုပ်ထားသော ကုဒ်ကို သီးသန့်လူနည်းစုသာသိသော အသိပညာများမပါဘဲ နားလည်နိုင်၊ တပ်ဆင်နိုင်၊ စမ်းသပ်နိုင်ပြီး ပြင်ဆင်ပြောင်းလဲနိုင်သည်အထိ ၎င်းကို တိုးတက်အောင် လုပ်ပါ။

အနည်းဆုံးအားဖြင့် command တစ်ခုတည်းဖြင့် တပ်ဆင်သတ်မှတ်ခြင်း၊ မြန်ဆန်၍ ရလဒ်သေချာသော စမ်းသပ်မှုလမ်းကြောင်းတစ်ခု၊ တည်ဆောက်ပုံပြ မြေပုံအကြမ်းတစ်ခု၊ ၎င်းတို့သက်ဆိုင်ရာ ကုဒ်များအနီးတွင်ရှိသော ဒေသန္တရ လုပ်ထုံးလုပ်နည်းများနှင့် စက်ဖြင့်ထိန်းကွပ်ထားသော တည်ဆောက်ပုံဆိုင်ရာ နယ်နိမိတ်တစ်ခုတို့ကို ထည့်ပါ။ အသစ်ဖြစ်သော ကိုယ်စားလှယ်တစ်ဦးထံသို့ ရီပိုကို အစ်ရှူး (issue) တစ်ခုနှင့် အပို ညွှန်ကြားပြသမှု မပါဘဲ ပေးပါ၊ ၎င်း လမ်းပျောက်သွားသည့် နေရာတိုင်းကို မှတ်တမ်းတင်ပါ။ ထို့နောက် အမှတ်ပြန်ပေးပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- ရှုထောင့်ငါးခုစလုံးအတွက် မလုပ်ဆောင်မီနှင့် လုပ်ဆောင်ပြီး ကိုယ်စားလှယ်အတွက် အသင့်ဖြစ်မှု အမှတ်များသည် အထောက်အထားနှင့်တကွ ရှိနေရမည်။
- command တစ်ခုက အသစ် clone လုပ်ထားသည်ကို တပ်ဆင်ပေးရမည်၊ command တစ်ခုက ရလဒ်သေချာသော စမ်းသပ်မှုလမ်းကြောင်းကို 2 မိနစ်အောက်အတွင်း အလုပ်လုပ်ပေးရမည်။
- ချိုးဖောက်ပါက CI ကို ကျရှုံးစေမည့် စစ်ဆေးမှုတစ်ခုဖြင့် တည်ဆောက်ပုံဆိုင်ရာ နယ်နိမိတ်တစ်ခုကို အတင်းအကျပ် ထိန်းကွပ်ထားရမည်။
- အသစ်ဖြစ်သော ကိုယ်စားလှယ် စမ်းသပ်မှုကို ရှုပ်ထွေးသွားသော အချက်တိုင်းနှင့် သင်ပြုလုပ်ခဲ့သော ပြင်ဆင်မှုတို့ဖြင့် လော့ဂ် မှတ်တမ်းတင်ခြင်း (logging) ပြုလုပ်ထားရမည်။

## ရက်သတ္တပတ် 6 — ကိုယ်စားလှယ်အခြေပြု ကုဒ်ရီဗျူး

**Focus:** AI ကုဒ်ရီဗျူး (code review) သည် မည်သည့်အရာများကို ကောင်းစွာဖမ်းထုတ်နိုင်ပြီး မည်သည့်အရာများကို လွဲမှားတတ်သည်၊ စစ်ဆေးသူ (reviewer) ဗိသုကာများနှင့် စိတ်ကြိုက်ပြင်ဆင်ထားသော စည်းမျဉ်းများ၊ AI ကုဒ်ရီဗျူးကို အဖွဲ့၏ ပူးလ်ရီကွက်စ် (pull request) လုပ်ငန်းစဉ် (workflow) တွင် ထည့်သွင်းအသုံးပြုခြင်း။

2. **Free book chapter:** *Software Engineering at Google*, [Chapter 9: Code Review](https://abseil.io/resources/swe-book/html/ch09.html) (45 min)။
3. **Talk:** Graphite မှ Tomas Reimers, [AI-powered entomology: lessons from millions of AI code reviews](https://ai.engineer/talks/TswQeKftnaw-ai-powered-entomology-lessons-from-millions-ai) (10 min), Graphite ၏ ရေးသားထားသော [AI code review implementation and best practices](https://graphite.dev/guides/ai-code-review-implementation-best-practices) (20 min) နှင့်အတူ။
4. **Review architecture:** Ankit Jain, [How to Kill the Code Review](https://ai.engineer/talks/how-to-kill-the-code-review) (16 min) — စပက် (specification) များ၊ ပြန်လည်အသုံးပြုနိုင်သော ဘေးကင်းလုံခြုံရေး ထိန်းကွပ်ချက် (guardrail) များ၊ ရလဒ်သေချာသော စစ်ဆေးမှု (deterministic check) များ၊ အကောင်အထည်ဖော်ဆောင်ရွက်နိုင်သော စမ်းသပ်မှုအစီအစဉ်များ၊ စမ်းသပ်ကြည့်ရှုမှုများနှင့် လူကိုယ်တိုင် ညှိနှိုင်းဆောင်ရွက်မှုတို့ကို ပေါင်းစပ်ထားသည့် ငါးလွှာပါဝင်သော ယုံကြည်စိတ်ချရမှု ပုံစံ။
5. **What automation cannot replace:** Geoffrey Litt, [Understanding Is the New Bottleneck](https://ai.engineer/talks/understanding-is-the-new-bottleneck) (20 min) — ကုဒ်မှန်ကန်မှုကို စစ်ဆေးခြင်းသက်သက်မဟုတ်ဘဲ ဗိသုကာဆိုင်ရာ နားလည်သဘောပေါက်မှု၊ လမ်းညွှန်သင်ပြမှုနှင့် ပေါင်းစပ်ညှိနှိုင်းမှုဆိုင်ရာ ရီဗျူးအဖြစ် ရှုမြင်ခြင်း။
6. **Integrations:** GitHub, [About GitHub Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review) (15 min) နှင့် Anthropic, [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions) (15 min) — ပူးလ်ရီကွက်စ်တစ်ခုတွင် စစ်ဆေးသူ ကိုယ်စားလှယ် (agent) ထည့်သွင်းသည့် အသုံးအများဆုံး နည်းလမ်းနှစ်ခု။

### တည်ဆောက်ခြင်း

ပြင်းထန်မှုအလိုက် စီစဉ်ထားသော ရီဗျူးစံနှုန်းသတ်မှတ်ချက်ကို ဖန်တီးပါ- မှန်ကန်မှု၊ လုံခြုံရေး၊ အချက်အလက် ဆုံးရှုံးမှု၊ ပြိုင်တူလုပ်ဆောင်နိုင်စွမ်း၊ ကိုက်ညီဆီလျော်မှု၊ စမ်းသပ်မှုများ၊ ထိန်းသိမ်းရလွယ်ကူမှု၊ ထို့နောက် အရေးအသားပုံစံ။ စစ်ဆေးသူ ကိုယ်စားလှယ်ကို အတိအကျလိုင်းများကို ကိုးကားရန်၊ ပျက်ကွက်မှုဖြစ်စဉ်ကို ရှင်းပြရန်နှင့် အသေးငယ်ဆုံး ပြင်ဆင်မှုကို အဆိုပြုရန် တောင်းဆိုပါ။ ပြောင်းလဲမှုကို ရေးသားခဲ့ခြင်းမရှိသော မော်ဒယ် (model)/ဆရှင် (session) ကို အသုံးပြုပါ။ အထက်ပါ ချိတ်ဆက်မှုတစ်ခုခုကို အသုံးပြု၍ သင်၏ ပူးလ်ရီကွက်စ်များနှင့် ချိတ်ဆက်ပါ။

စစ်ဆေးသူကို အနည်းဆုံး ပူးလ်ရီကွက်စ် ငါးခုတွင် အကဲဖြတ်ပါ (evaluation)၊ သိမ်မွေ့သော ဘဂ်များ ရည်ရွယ်ချက်ရှိရှိ ထည့်သွင်းထားသည့် ပူးလ်ရီကွက်စ် တစ်ခုပါဝင်သည်။ မှတ်ချက်တိုင်းကို true positive၊ false positive၊ duplicate သို့မဟုတ် low-value ဟု အမှတ်အသားပြုပါ။ လက်ခံအသုံးပြုမှု (adoption) နှုန်းနှင့် လွတ်ကင်းသွားသော ချို့ယွင်းချက်များကို ခြေရာခံပါ။ လူတစ်ဦးသည် မာ့ချ် (merge) အတည်ပြုချက် (approval) ကို ပိုင်ဆိုင်ဆဲဖြစ်သည်။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- စံနှုန်းသတ်မှတ်ချက်ကို စစ်ဆေးပြီးဖြစ်၍ စစ်ဆေးသူ ကိုယ်စားလှယ်သည် ပူးလ်ရီကွက်စ်များတွင် အလိုအလျောက် အလုပ်လုပ်သည်။
- စစ်ဆေးပြီးသော ပူးလ်ရီကွက်စ် ငါးခုတွင် မှတ်ချက်တိုင်းကို အမှတ်အသားပြုထားပြီး တိကျမှုကို တွက်ချက်ထားသည်။
- ရည်ရွယ်ချက်ရှိရှိ ထည့်သွင်းထားသော ဘဂ်ပါသည့် ပူးလ်ရီကွက်စ် အစီရင်ခံစာတွင် မည်သည့် ဘဂ်များကို ဖမ်းမိပြီး မည်သည့် ဘဂ်များ လွတ်ကင်းသွားသည်ကို ဖော်ပြထားသည်။
- စာပိုဒ်တစ်ပိုဒ်တွင် စစ်ဆေးသူ စနစ်တကျ လွဲမှားတတ်သည့် အရာများနှင့် ယခုအခါ မည်သည့် ရလဒ်သေချာသော စစ်ဆေးမှုက ၎င်းကို လွှမ်းခြုံထားကြောင်း မှတ်တမ်းတင်ထားသည်။

## ရက်သတ္တပတ် 7 — လုံခြုံရေး (Security)

**အဓိကထားမည့်အရာ:** SAST/SCA၊ မှီခိုမှုနှင့် လျှို့ဝှက်ချက် နှင့် ဝင်ရောက်ခွင့်အထောက်အထား (secret / credential) ယိုစိမ့်မှု အားနည်းချက်များ၊ ပရွမ့်ထဲသို့ အန္တရာယ်ရှိကုဒ်ထည့်သွင်းခြင်း (prompt injection) နှင့် ကိုယ်စားလှယ် (agent) သီးသန့် တိုက်ခိုက်နိုင်သော မျက်နှာပြင်များ၊ ကိုယ်စားလှယ် ကူညီပံ့ပိုးမှုဖြင့် ပြဿနာ ခွဲခြားဆန်းစစ်ခြင်းနှင့် ဖြေရှင်းပြုပြင်ခြင်း။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 h 50 min)

1. **ခြိမ်းခြောက်မှုပုံစံ (threat model) စာရင်းများ:** [OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/) (30 min) နှင့် [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) (30 min)။
2. **ကိုယ်စားလှယ် သီးသန့် ဘောင်ခတ်ကြည့်မြင်ခြင်း:** Simon Willison၊ [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) (10 min) နှင့် [Prompt injection explained](https://simonwillison.net/2023/May/2/prompt-injection-explained/) (စာသားပါဝင်သော ဟောပြောချက်၊ 15 min)။
3. **လက်တွေ့ တိုက်ခိုက်မှု:** Embrace The Red၊ [GitHub Copilot: Remote Code Execution via Prompt Injection (CVE-2025-53773)](https://embracethered.com/blog/posts/2025/github-copilot-remote-code-execution-via-prompt-injection/) (15 min) — ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် (coding agent) ကို တိုက်ခိုက်သည့် အစဉ်လိုက် လုပ်ငန်းစဉ် အစမှ အဆုံးအထိ။
4. **ဗီဒီယို:** Semgrep မှ Isaac Evans၊ [When AI Writes Code: Rethinking App Security](https://www.youtube.com/watch?v=TKJGul9TRws) (45 min) — AI ဖန်တီးပေးသော အားနည်းချက်များ၊ SAST၊ လုံခြုံရေး ကူညီပံ့ပိုးသူများ၊ တုံ့ပြန်မှု စက်ဝန်းများ နှင့် ကုဒ်ရေးပေးသော ကိုယ်စားလှယ်များ ကြောင့် ဖြစ်ပေါ်လာသော အန္တရာယ်များ။
5. **လက်တွေ့လေ့ကျင့်မှု:** Semgrep၊ [Finding vulnerabilities in modern web apps using Claude Code and OpenAI Codex](https://semgrep.dev/blog/2025/finding-vulnerabilities-in-modern-web-apps-using-claude-code-and-openai-codex/) (20 min) — လက်တွေ့တွင် ကိုယ်စားလှယ် ကူညီပံ့ပိုးမှုဖြင့် ပြဿနာ ခွဲခြားဆန်းစစ်ခြင်း။
6. **ကုဒ်ရေးပေးသော ကိုယ်စားလှယ် ခြိမ်းခြောက်မှုပုံစံ:** OpenAI မှ Fouad Matin၊ [Safety and Security for Code-Executing Agents](https://ai.engineer/talks/safety-and-security-for-code-executing-agents) (14 min) — အဝေးမှ ကုဒ်ပရိုဂရမ် စတင်လိုက်ပါစေခြင်း၊ ပရွမ့်ထဲသို့ အန္တရာယ်ရှိကုဒ်ထည့်သွင်းခြင်း၊ အချက်အလက် ခိုးယူထုတ်ယူခြင်း၊ ကွန်တိန်နာများ၊ ကွန်ရက် ကန့်သတ်ချက်များ၊ လူကိုယ်တိုင် အတည်ပြုချက် (human approval) များ နှင့် OS-အဆင့် ဆန်းဘောက်စ် (sandbox)။
7. **လက်တွေ့လေ့ကျင့်ခန်းများ:** PortSwigger၊ [Web Security Academy](https://portswigger.net/web-security) — သွယ်ဝိုက်သော ပရွမ့်ထဲသို့ အန္တရာယ်ရှိကုဒ်ထည့်သွင်းခြင်း အပါအဝင် Web LLM attacks လက်တွေ့လေ့ကျင့်ခန်းများကို ပြုလုပ်ပါ (လက်တွေ့လေ့ကျင့်ခန်း နှစ်ခုအတွက် ≈ 60 min)။

- **Lab companion:** Rana Khalil၊ [Web Security Academy series introduction](https://www.youtube.com/watch?v=GdMTzcn5F0c) (12 min)။

### စာအုပ်

- Adam Shostack၊ [*Threat Modeling: Designing for Security*](https://shostack.org/archive/2014/02/threat-modeling-designing-for-security/) — ပထမအကြိမ်ထုတ် ပုံနှိပ်ခြင်းကို အသုံးပြုပါ၊ AI ကမ္ဘာအတွက် ခေါင်းစဉ်သစ်တပ်ထားသော [second edition](https://shostack.org/books/threat-modeling-book) ကို 2027 ဖေဖော်ဝါရီအတွက် ကြေညာထားသည်။

### တည်ဆောက်ခြင်း

ကိုယ်စားလှယ် လုပ်ငန်းစဉ်စက်ဝန်း (agent loop) တစ်ခုလုံး၏ ခြိမ်းခြောက်မှုပုံစံ (threat model) ကို ဆန်းစစ်ပါ- အသုံးပြုသူ၏ ထည့်သွင်းချက်၊ ရီပို (repository) ပါဝင်အချက်အလက်၊ ရှာဖွေရရှိသော ဝဘ်စာမျက်နှာများ၊ ကိရိယာ (tool) များ၊ လျှို့ဝှက်ချက် နှင့် ဝင်ရောက်ခွင့်အထောက်အထားများ၊ MCP server များ၊ ထုတ်လုပ်ထားသော အမိန့်ပေးချက်များ၊ လော့ဂ် မှတ်တမ်းတင်ခြင်း (logging) များ၊ နှင့် တပ်ဆင်ဖြန့်ကြက်မှု။ အနည်းဆုံး လုပ်ပိုင်ခွင့် (least privilege)၊ တိကျသော ခွင့်ပြုစာရင်း (allowlist) များ၊ လျှို့ဝှက်ချက်များ သီးခြားခွဲထုတ်ခြင်း၊ ဆန်းဘောက်စ် (sandbox) ပြုလုပ်ခြင်း၊ နှင့် ပြန်ပြင်၍မရနိုင်သော လုပ်ဆောင်ချက်များအတွက် လူကိုယ်တိုင် အတည်ပြုချက် (human approval) တို့ကို အသုံးပြုပါ။

SAST (Semgrep သို့မဟုတ် CodeQL)၊ မှီခိုမှု/SCA (OSV-Scanner)၊ နှင့် လျှို့ဝှက်ချက် စကန်ဖတ်မှုများ (gitleaks) ကို CI တွင် စကန်ဖတ်မောင်းနှင်ပါ။ မယုံကြည်ရသော ဖိုင်အချက်အလက်ထဲတွင် အန္တရာယ်မရှိသော သွယ်ဝိုက်သော ပရွမ့်ထဲသို့ အန္တရာယ်ရှိကုဒ်ထည့်သွင်းခြင်း စာကြောင်းကို ထည့်သွင်းထားပြီး၊ ကိုယ်စားလှယ် (agent) က ၎င်းကို ညွှန်ကြားချက်အဖြစ် မဟုတ်ဘဲ အချက်အလက်အဖြစ်သာ သတ်မှတ်ကြောင်း စစ်ဆေးပါ။ လျှို့ဝှက်ချက်များ ပေါက်ကြားမှု၊ အန္တရာယ်ရှိသော ကိရိယာ ထွက်ရှိချက်၊ နှင့် ထိန်းချုပ်မရဘဲ မြင့်တက်သွားသော ကုန်ကျစရိတ် (cost) တို့အတွက် တိုတောင်းသော မမျှော်လင့်သော ပြဿနာရပ် လမ်းညွှန်ချက် စာအုပ်ကို ရေးသားပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- ခြိမ်းခြောက်မှုပုံစံ စာတမ်းသည် ကိုယ်စားလှယ် လုပ်ငန်းစဉ် တွင် ယုံကြည်ရမှု နယ်နိမိတ်တိုင်းကို နယ်နိမိတ်တစ်ခုစီအတွက် လျှော့ချရေးနည်းလမ်းဖြင့် စာရင်းပြုစုထားသည်။
- SAST၊ SCA၊ နှင့် လျှို့ဝှက်ချက် စကန်ဖတ်မှုများကို CI တွင် မောင်းနှင်ပြီး မြင့်မားသော အန္တရာယ်ရှိ တွေ့ရှိချက်များတွင် တားဆီးသည်။
- ထည့်သွင်းထားသော အန္တရာယ်ရှိကုဒ် စာကြောင်းကို လျစ်လျူရှုထားကြောင်း သက်သေပြနိုင်ပြီး မှတ်တမ်းကို သိမ်းဆည်းထားသည်။
- မမျှော်လင့်သော ပြဿနာရပ် လမ်းညွှန်ချက် စာအုပ်သည် အခြေအနေ သုံးခုလုံးအတွက် တာဝန်ရှိသူ တစ်ဦးစီနှင့် ပထမဆုံး အဆင့် သုံးဆင့်စီကို လွှမ်းခြုံထားသည်။

## ရက်သတ္တပတ် 8 — နောက်ကွယ်မှ အလုပ်လုပ်သော ကိုယ်စားလှယ်များ (Background Agents)

**Focus:** အချိန်ကိုက်စောင့်ဆိုင်းရန်မလိုသော မိုးတိမ်ပေါ်လွှဲပြောင်းလုပ်ဆောင်သည့် ကိုယ်စားလှယ်များ၊ ပြိုင်တူလုပ်ဆောင်သော ကိုယ်စားလှယ်အုပ်စု (fleet) များကို စီမံခန့်ခွဲခြင်း၊ အစ်ရှူး (issue) မှ ပူးလ်ရီကွက်စ် (PR) သို့ ချိတ်ဆက်သည့် လုပ်ငန်းစဉ်များ (pipelines) နှင့် Slack, Linear, GitHub တို့မှ စတင်လုပ်ဆောင်စေသည့် အစပျိုးချက်များ။

4. **Durable execution:** Temporal မှ Preeti Somal, [Scaling AI Agents Without Breaking Reliability](https://ai.engineer/talks/scaling-ai-agents-without-breaking-reliability) (15 min) — ရေရှည်တည်တံ့သော အခြေအနေ၊ ချိတ်ဆက်ညှိနှိုင်းစီမံခြင်း၊ စောင့်ကြည့်မြင်တွေ့နိုင်မှု၊ အလိုအလျောက် ပြန်လည်ကောင်းမွန်လာမှု၊ လူကိုယ်တိုင် ပါဝင်ဆောင်ရွက်မှု၊ နှင့် ပြိုင်တူလုပ်ဆောင်မှုများ။

- **အခြေခံအဆောက်အအုံ စီးပွားရေးဆိုင်ရာ -** Neil Movva၊ [Why AI Is About to Get 1000x Cheaper](https://www.youtube.com/watch?v=uyzqxIoiobU) (1 h 23 min; သက်ဆိုင်ရာ အခန်းများမှာ `05:32` တွင် ကြာရှည်စွာ အလုပ်လုပ်သော ကိုယ်စားလှယ်များ၊ `15:12` တွင် တွက်ချက်အဖြေထုတ်ခြင်း (inference) စတက်ခ်၊ `20:03` တွင် စွမ်းဆောင်ရည် အထွက်နှုန်းနှင့် ကြန့်ကြာချိန် (latency)၊ `33:19` တွင် တာန်းဖောမား ဟာ့ဒ်ဝဲ တို့ ဖြစ်ကြသည်)။ “1000x” ကို သက်သေပြပြီးသော ခန့်မှန်းချက်အဖြစ် မဟုတ်ဘဲ ရည်မှန်းချက်တစ်ခုအဖြစ် မှတ်ယူပါ။

### တည်ဆောက်ခြင်း

အစ်ရှူး (issue) မှ ပူးလ်ရီကွက်စ် (pull request) သို့ လုပ်ဆောင်ပေးသည့် နောက်ကွယ်မှ အလုပ်လုပ်သော လုပ်ငန်းစဉ် (background flow) တစ်ခုကို ဖန်တီးတည်ဆောက်ပါ။ အလုပ်တစ်ခုစီအတွက် သီးခြားခွဲထုတ်ထားသော အလုပ်လမ်းကြောင်း (worktree) သို့မဟုတ် ကွန်တိန်နာ၊ တင်းကြပ်သော ဘတ်ဂျက် (budget)၊ မှတ်တိုင် (checkpoint)၊ ရလဒ်သေချာသော စစ်ဆေးမှု (deterministic validation) နှင့် ပြန်လည်စတင်နိုင်သော အခြေအနေတို့ ပါဝင်ရပါမည်။ ကန့်သတ်ထားသော စောင့်ဆိုင်းချိန်ဖြင့် ထပ်မံကြိုးစားခြင်း (retry) များကို ထည့်သွင်းပါ၊ ကိုယ်စားလှယ် နှစ်ခုမှ လုပ်ဆောင်ရန် အရာတစ်ခုတည်းကို တစ်ပြိုင်နက်တည်း တည်းဖြတ်ခြင်းမရှိစေရန် တားဆီးပါ။

လုပ်ဆောင်ချက် သုံးခုကို ပြိုင်တူ လုပ်ဆောင်ပါ - လုပ်ဆောင်ချက် သေးသေးတစ်ခု၊ ဘဂ်ပြင်ဆင်မှု တစ်ခု၊ နှင့် မှတ်တမ်းအချက်အလက် ရေးသားသည့် အလုပ်တစ်ခု။ တစ်ခုကို လမ်းဝက်တွင် နှောင့်ယှက်လိုက်ပြီး ၎င်းသည် ပြန်လည်စတင်နိုင်ကြောင်း သို့မဟုတ် သပ်ရပ်စွာ ပျက်ကွက်ကြောင်း ပြသပါ။ ကိုယ်စားလှယ်များသည် ပူးလ်ရီကွက်စ်များ ပွင့်သွားနိုင်သည်၊ လူကိုယ်တိုင် အတည်ပြုချက် (human approval) ရှိသူသာလျှင် မာ့ချ် (merge) လုပ်နိုင်သည်။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- အစ်ရှူး သုံးခုမှ ပြိုင်တူ အလုပ် သုံးခု လုပ်ဆောင်ခဲ့ပြီး တစ်ခုစီသည် အခြားအရာများ၏ ဖိုင်များကို တည်းဖြတ်ခြင်းမရှိဘဲ ပူးလ်ရီကွက်စ် တစ်ခုစီ ဖွင့်လှစ်ခဲ့သည်။
- နှောင့်ယှက်ခံလိုက်ရသော အလုပ်သည် ၎င်း၏ မှတ်တိုင်မှ ပြန်လည်စတင်ခဲ့သည် သို့မဟုတ် ရှင်းလင်းသော အခြေအနေဖြင့် ပျက်ကွက်ခဲ့ပြီး၊ မည်သည့်အရာ ဖြစ်သည်ကို လော့ဂ် မှတ်တမ်းတင်ခြင်း (logging) မှ သက်သေပြသည်။
- အလုပ်တစ်ခုစီသည် ၎င်း၏ ဘတ်ဂျက်အောက်တွင် ရှိနေခဲ့ပြီး၊ ဘတ်ဂျက် ကန့်သတ်ချက်ကျော်လွန်သည့် လမ်းကြောင်းကို အနည်းဆုံး တစ်ကြိမ် စမ်းသပ်ခဲ့သည်။
- နှိုင်းယှဉ်ချက် မှတ်စုတစ်ခုသည် အထက်ပါ ဟို့စ်လုပ်ထားသော ထုတ်ကုန်များကို တောက်လျှောက်လုပ်ဆောင်မှု၊ သီးခြားခွဲထုတ်မှု၊ နှင့် အတည်ပြုချက် ပုံစံတို့ပေါ် မူတည်၍ အဆင့်သတ်မှတ်ပေးသည်။

## ရက်သတ္တပတ် 9 — AI-Native အဖွဲ့တစ်ဖွဲ့ တည်ဆောက်ခြင်း

**အဓိကထားမည့်အရာ:** MCP ဗဟိုဝင်ပေါက်များ (portals) နှင့် ဗဟိုချုပ်ကိုင်ထားသော၊ ခွင့်ပြုချက် (permission) လိုအပ်သည့် ကိရိယာ (tool) ရယူသုံးစွဲခွင့်၊ LLM ဝင်ပေါက်များ (gateways)၊ မော်ဒယ် (model) လမ်းကြောင်းသတ်မှတ်ပေးခြင်း (routing) နှင့် ကုန်ကျစရိတ် (cost) အကောင်းဆုံးဖြစ်အောင် ပြုလုပ်ခြင်း၊ အဖွဲ့အစည်းတစ်ဝန်း လက်ခံအသုံးပြုမှု (adoption) ပုံစံများ။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 h 40 min)

### တည်ဆောက်ခြင်း

သင်၏ မော်ဒယ် (model) ခေါ်ယူမှုများကို ဝင်ပေါက် (gateway) သို့မဟုတ် ပရော့ဆီ တစ်ခု (LiteLLM သို့မဟုတ် Cloudflare AI Gateway) ၏ နောက်ကွယ်တွင် ထားရှိပါ။ ကိုယ်စားလှယ် (agent) အလိုက် မည်သူမည်ဝါဖြစ်ကြောင်း သတ်မှတ်ချက်၊ ဘတ်ဂျက် (budget) များ၊ မော်ဒယ် လမ်းကြောင်းသတ်မှတ်ပေးခြင်း (routing)၊ ပျက်ကွက်ပါက အစားထိုး လုပ်ဆောင်မည့် အပြုအမူ၊ ကုန်ကျစရိတ် (cost) နှင့် ကြန့်ကြာချိန် (latency) လော့ဂ် မှတ်တမ်းတင်ခြင်း (logging) များနှင့် ပြင်ပသို့ မပေါက်ကြားစေရန် ပိတ်ပင်သည့် နည်းဥပဒေများကို ထည့်သွင်းပါ။ ခွင့်ပြုစာရင်း (allowlist) သွင်းထားသော ကိရိယာ (tool) များ၊ တိကျသော နယ်ပယ်များ၊ စစ်ဆေးရေးမှတ်တမ်း (audit log) များနှင့် ရုပ်သိမ်းနိုင်သော ဝင်ရောက်ခွင့်အထောက်အထားများ ပါဝင်သည့် သေးငယ်သော MCP ဗဟိုဝင်ပေါက် (portal) တစ်ခုကို ဖန်တီးပါ။

ခွင့်ပြုထားသော အချက်အလက်များ၊ မဖြစ်မနေ လူကိုယ်တိုင် အတည်ပြုချက် (human approval) ယူရမည့် ဆုံးဖြတ်ချက်များ၊ မမျှော်လင့်သော ပြဿနာရပ် (incident) စီမံခန့်ခွဲမှု တာဝန်ယူမှု၊ ကုဒ်ရီဗျူး လိုအပ်ချက်များနှင့် မည်သည့် တိုင်းတာချက်များက အရေးပါတယ်ဆိုသည်ကို လွှမ်းခြုံထားသည့် တစ်စာမျက်နှာပါ အဖွဲ့လိုက် လက်ခံအသုံးပြုမှု မူဝါဒကို ရေးသားပါ။ ကုဒ်ကြောင်းရေ ထက် ပြောင်းလဲမှု ဖျက်ဆီးနိုင်ခြေ နှုန်း၊ ကြာမြင့်ချိန်၊ ကုဒ်ရီဗျူး ဝန်ထုပ်ဝန်ပိုး၊ ကုန်ကျစရိတ် နှင့် အတည်ပြုပြီးသား လုပ်ငန်းစဉ် အောင်မြင်မှု တို့ကို ပိုမို ဦးစားပေးပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- သင်၏ စနစ်အတွင်းရှိ မော်ဒယ် ခေါ်ယူမှုတိုင်းသည် ဝင်ပေါက်မှတစ်ဆင့် သွားရမည်။ တိုက်ရိုက် ခေါ်ယူမှုကို ပိတ်ဆို့မည် သို့မဟုတ် ချိုးဖောက်မှုအဖြစ် လော့ဂ် မှတ်တမ်းတင်မည်ဖြစ်သည်။
- လမ်းကြောင်းသတ်မှတ်ပေးခြင်းသည် အနည်းဆုံး တောင်းဆိုမှု အမျိုးအစား တစ်ခုကို ပိုမို သက်သာသော မော်ဒယ်ထံ သို့ ပို့ဆောင်ပေးမည် ဖြစ်ပြီး ကုန်ကျစရိတ် လော့ဂ်တွင် သက်သာသွားမှုကို ပြသမည်ဖြစ်သည်။
- MCP ဗဟိုဝင်ပေါက်သည် ခွင့်ပြုစာရင်း သွင်းထားသော ကိရိယာများကိုသာ ထုတ်ဖော် ပြသမည် ဖြစ်ပြီး ဝင်ရောက်ခွင့်အထောက်အထား တစ်ခုကို ရုပ်သိမ်းလိုက်ပါက လုပ်ဆောင်မှု စက်ဝန်း တစ်ခုအတွင်း သုံးစွဲခွင့် ပိတ်သွားမည်ဖြစ်သည်။
- လက်ခံအသုံးပြုမှု မူဝါဒသည် စာမျက်နှာ တစ်ခုတည်းတွင် ဆံ့ဝင်မည် ဖြစ်ပြီး မမျှော်လင့်သော ပြဿနာရပ်များအတွက် တာဝန်ရှိသူကို အမည်တပ် ဖော်ပြထားမည်ဖြစ်သည်။

## ရက်သတ္တပတ် 10 — ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ (The Software Factory) + အနာဂတ်

**Focus:** မိမိကိုယ်ကို အလိုအလျောက် ပတ်မောင်းနိုင်ပြီး မိမိကိုယ်ကို တိုးတက်အောင်လုပ်နိုင်စွမ်း (self-improving) ရှိသော ဆော့ဖ်ဝဲစနစ်များ၊ ကိုယ်စားလှယ် (agent) များကို တပ်ဆင်အသုံးပြုပြီးနောက်ပိုင်း ပတ်မောင်းခြင်းနှင့် ဘေးကင်းလုံခြုံအောင် ဆောင်ရွက်ခြင်း၊ AI ဆော့ဖ်ဝဲအင်ဂျင်နီယာဘာသာရပ် ရှေ့ဆက်သွားမည့် လမ်းကြောင်း။

### အခြေခံကျသော သင်ခန်းစာ (core material) (≈ 3 h 30 min)

1. **Keynote:** Andrej Karpathy, [Software Is Changing (Again)](https://www.youtube.com/watch?v=LCEmiRjPEtQ) (39 min).
2. **Current case study:** Warp, [The self-improvement loop in a software factory](https://www.warp.dev/articles/self-improvement-loop-software-factory) (20 min).
3. **Critical counterargument:** Dex Horthy, [Harness Engineering Is Not Enough: Why Software Factories Fail](https://ai.engineer/talks/harness-engineering-is-not-enough-why-software-factories-fail) (19 min) — brownfield ထိန်းသိမ်းရလွယ်ကူမှု၊ အားနည်းသော ကုဒ်ရီဗျူး (code review)၊ မမျှော်လင့်သော ပြဿနာရပ် (incident) များနှင့် ပမာဏများပြားသော ကိုယ်စားလှယ်၏ ထွက်ရှိချက်များအောက်တွင် ဗိသုကာဆိုင်ရာ ယိုယွင်းပျက်စီးမှု။
4. **Post-deployment operations:** [Always-on agents run production without the on-call tax](https://ai.engineer/talks/always-on-agents-run-production-without-the-on-call-tax) (25 min) နှင့် Google SRE, [Postmortem Culture: Learning from Failure](https://sre.google/sre-book/postmortem-culture/) (30 min) — ကိုယ်စားလှယ်များ ပတ်မောင်းထားသော စနစ်များအတွက် ယနေ့ထက်တိုင် လိုအပ်နေသေးသည့် စနစ်လည်ပတ်ရေးဆိုင်ရာ စည်းကမ်း။
5. **Tracing and evals:** Arize AI, [How to Debug AI Agents: Tracing, Observability & Evals](https://www.youtube.com/watch?v=nWNWrtCDqaY) (19 min) နှင့် Arize Phoenix, [Your First Traces](https://arize.com/docs/phoenix/tracing/tutorial/your-first-traces) (30 min လက်တွေ့စမ်းသပ်မှု)။
6. **System design:** စက်ရုံ တည်ဆောက်ရေးကို စိတ်ထဲ၌ ထားရှိပြီး OpenAI ၏ [Symphony article](https://openai.com/index/open-source-codex-orchestration-symphony/) နှင့် [specification](https://github.com/openai/symphony/blob/main/SPEC.md) များကို ပြန်လည်လေ့လာပါ (20 min)။

### ကိရိယာများနှင့် ကိုးကားချက်များ

- **Evals course:** DeepLearning.AI, [Evaluating AI Agents](https://www.deeplearning.ai/courses/evaluating-ai-agents) (≈ 2 h) — ခြေရာခံ မှတ်တမ်းတင်ခြင်း (tracing)၊ ပါဝင်သောအစိတ်အပိုင်းနှင့် လမ်းကြောင်းအကဲဖြတ်ခြင်း၊ LLM ဒိုင်လူကြီးများ၊ နှင့် ထုတ်လုပ်မှုအဆင့် စောင့်ကြည့်စစ်ဆေးခြင်း။
- စောင့်ကြည့်လေ့လာနိုင်စွမ်း (Observability): [Langfuse](https://langfuse.com/docs) (Phoenix ၏ အခမဲ့ရယူနိုင်သော မူရင်းကုဒ် အစားထိုးစနစ်) နှင့် [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai)။
- Controlled improvement loops: [DSPy](https://dspy.ai/) — ပရွမ့် (prompt) များကို ကိုယ်တိုင် ပြင်ဆင်ရေးသားမည့်အစား သင့် အကဲဖြတ်ခြင်း (eval) အစုအဝေးပေါ် မူတည်၍ ကောင်းမွန်အောင် ပြုပြင်ပါ။
- Benchmarks to borrow task design from: [SWE-bench](https://www.swebench.com/) နှင့် [Terminal-Bench](https://www.tbench.ai/)။
- Google SRE, [Introduction](https://sre.google/sre-book/introduction/)။

### ထပ်ဆောင်း ဗီဒီယို သင်ခန်းစာများ

- **အကဲဖြတ်ခြင်း (eval) များကို အသေးစိတ် လေ့လာခြင်း:** Lenny's Podcast တွင် Hamel Husain နှင့် Shreya Shankar တို့ ပြောကြားထားသော [Why AI evals are the hottest new skill for product builders](https://www.youtube.com/watch?v=BsWxPI9UM4c) (1 h 46 min) — အမှားအယွင်း ခွဲခြမ်းစိတ်ဖြာခြင်း၊ LLM-as-judge စစ်ဆေးအတည်ပြုခြင်း နှင့် အကဲဖြတ်ခြင်း (eval) လုပ်ငန်းစဉ် (workflow)။
- **ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ (software factory) အယူအဆ:** Eno Reyes ၏ [The Software Factory](https://ai-in-the-am.com/episodes/ai-am-2026-06-18/) — ကိုယ်စားလှယ်အတွက် အသင့်ဖြစ်မှု (agent readiness)၊ ရလဒ်သေချာသော စစ်ဆေးမှု (deterministic) စနစ်များ၊ ထိန်းချုပ်စမ်းသပ်စနစ် (harness) များ၊ တုံ့ပြန်မှုဆိုင်ရာ လုပ်ငန်းစဉ်စက်ဝန်းများ နှင့် ကိုယ်စားလှယ် (agent) အလုပ်များအတွက် ရင်းနှီးမြှုပ်နှံမှု ခွဲဝေပေးသည့် အဖွဲ့အစည်းများအကြောင်း အချိန်မှတ်တမ်းပါ စက်ရှင်တစ်ခု။
- **ကိုယ်စားလှယ်များ၏ ဆယ်စုနှစ်:** Dwarkesh Patel နှင့် Andrej Karpathy တို့၏ [“We're summoning ghosts, not building animals”](https://www.youtube.com/watch?v=lXUZvyajciY) (2 h 26 min) — ကိုယ်စားလှယ်များသည် အဘယ်ကြောင့် အစီအစဉ် (plan) ဆွဲရန်၊ မှတ်မိရန် သို့မဟုတ် ဗဟုသုတများကို စုဆောင်းရန် မလုပ်ဆောင်နိုင်သေးရသည့် အကြောင်းအရင်း နှင့် နောက်လာမည့် ဆယ်စုနှစ်အတွက် ယင်း၏ အဓိပ္ပာယ်။
- **ကျယ်ပြန့်သော လက်တွေ့လုပ်ဆောင်သူများ၏ စုစည်းသုံးသပ်ချက်:** DHH ၏ [Future of Programming and Agentic Engineering](https://www.youtube.com/watch?v=NYFGCESmikA) ကို ပြန်လည်ကြည့်ရှုပါ။ အထူးသဖြင့် ဆော့ဖ်ဝဲရေးသားခြင်း၏ အနာဂတ်အကြောင်း `3:59:24` ကို ကြည့်ပါ။ ယင်းကို နည်းပညာဆိုင်ရာ အခွင့်အာဏာတစ်ခုအနေဖြင့် မဟုတ်ဘဲ ရှုထောင့်တစ်ခုအနေဖြင့် အသုံးပြုပါ။

### တည်ဆောက်ခြင်း

အစိတ်အပိုင်းများကို အနည်းဆုံး ဆော့ဖ်ဝဲထုတ်လုပ်ရေးစက်ရုံ တစ်ခုအဖြစ် ချိတ်ဆက်ပါ -

`issue → aligned spec → isolated agent run → tests/checks → independent review → human merge`

လုပ်ဆောင်မှုတိုင်းကို ခြေရာခံ မှတ်တမ်းတင်ခြင်း (trace) ပြုလုပ်ပါ။ ကိုယ်စားပြု လုပ်ငန်းစဉ် 10–20 ခုပါဝင်သော သေချာသတ်မှတ်ထားသည့် အကဲဖြတ်ခြင်း အစုအဝေးတစ်ခုကို ဖန်တီးပြီး အောင်မြင်မှု၊ ယခင်အလုပ်လုပ်ပြီးသားများ ပြန်လည်ချို့ယွင်းမှု (regression)၊ ကုန်ကျစရိတ် (cost)၊ ကြန့်ကြာချိန် (latency)၊ ထပ်မံကြိုးစားခြင်း (retry) များ နှင့် လူကိုယ်တိုင် ဝင်ရောက်ဆောင်ရွက်မှုများကို မှတ်တမ်းတင်ပါ။ ပရွမ့် (prompt) များ၊ ကျွမ်းကျင်မှု (skill) များ သို့မဟုတ် ကိရိယာ (tool) များကို ပြောင်းလဲရန် အဆိုပြုနိုင်သော်လည်း အကဲဖြတ်ခြင်း နှင့် လူကိုယ်တိုင် အတည်ပြုချက် (human approval) မပါဘဲ ထိုပြောင်းလဲမှုများကို မဖြန့်ကြက်နိုင်သော ထိန်းချုပ်ထားသည့် တိုးတက်မှုဆိုင်ရာ လုပ်ငန်းစဉ်စက်ဝန်းတစ်ခု ထည့်သွင်းပါ။ "မိမိကိုယ်ကို တိုးတက်အောင်လုပ်နိုင်စွမ်း (self-improving)" ဆိုသည်မှာ "မိမိ၏ ထိန်းချုပ်မှုများကို တိတ်တဆိတ် ပြန်လည်ရေးသားခြင်း" ဟု မဆိုလိုပါ။

ရက်သတ္တပတ် 10 အတွင်း စက်ရုံမှ ထွက်ပေါ်ခဲ့သော အဆိုးရွားဆုံး ပျက်ကွက်မှုအတွက် မည်သူ့ကိုမျှ အပြစ်မတင်သော ပြဿနာဖြစ်ပြီးနောက် ပြန်လည်သုံးသပ်ခြင်း (postmortem) တစ်ခု ရေးသားပါ။

### ပြီးစီးမှု သတ်မှတ်ချက်များ (Done when)

- စက်ရုံ၏ လုပ်ဆောင်မှုတိုင်းကို Phoenix သို့မဟုတ် Langfuse တွင် အစ်ရှူး (issue) မှသည် မာ့ချ် (merge) ဆုံးဖြတ်ချက်အထိ ခြေရာခံ မှတ်တမ်းတင်နိုင်ရမည်။
- အကဲဖြတ်ခြင်း အစုအဝေးတွင် အနည်းဆုံး လုပ်ငန်းစဉ် 10 ခုအတွက် အခြေခံ နှင့် နောက်ဆုံး ရလဒ်များ ရှိရမည်။
- တိုးတက်မှုဆိုင်ရာ လုပ်ငန်းစဉ်စက်ဝန်းသည် အနည်းဆုံး ပြောင်းလဲမှုတစ်ခုကို အဆိုပြုထားရမည်ဖြစ်ပြီး၊ ထိုပြောင်းလဲမှုကို လူတစ်ဦးမှ အတည်ပြုခြင်း သို့မဟုတ် ငြင်းပယ်ခြင်း မပြုမီ အကဲဖြတ်ထားရမည်။
- အချိန်ဇယား၊ အဓိက အကြောင်းအရင်း နှင့် ထပ်မံမဖြစ်ပွားအောင် တားဆီးပေးသည့် ပြောင်းလဲမှုတစ်ခု ပါဝင်သော ပြဿနာဖြစ်ပြီးနောက် ပြန်လည်သုံးသပ်ခြင်း တစ်ခု ရှိရမည်။

## အကြံပြုထားသော အဆုံးသတ် စီမံကိန်း (capstone)

**အစစ်အမှန် ရီပို (repository) တစ်ခုအတွက် ကိုယ်စားလှယ် (agent) ကိုအခြေခံသော ပြုပြင်ထိန်းသိမ်းရေးစနစ်**ကို တည်ဆောက်ပါ။ ၎င်းသည် သေချာစွာသတ်မှတ်ထားသော အစ်ရှူး (issue) တစ်ခုကို လက်ခံရမည်ဖြစ်ပြီး၊ သီးခြားခွဲထုတ်ထားသော အလုပ်လုပ်ရာနေရာတစ်ခု ဖန်တီးခြင်း၊ အပြောင်းအလဲအတွက် လေ့လာစူးစမ်းခြင်း (research) နှင့် အစီအစဉ် (plan) ရေးဆွဲခြင်း၊ ၎င်းကို အကောင်အထည်ဖော် ရေးသားခြင်း (implement)၊ ရီပို စစ်ဆေးမှုများကို လုပ်ဆောင်ခြင်း၊ သီးခြားလွတ်လပ်သော AI သုံးသပ်မှု လုပ်ဆောင်ခြင်း၊ နှင့် လူကိုယ်တိုင် အတည်ပြုချက် (human approval) ရယူရန်အတွက် ပူးလ်ရီကွက်စ် (pull request) တစ်ခု ဖွင့်ပေးခြင်းတို့ကို လုပ်ဆောင်ရမည်။

### ပေးအပ်ရမည့် ရလဒ်များ (deliverables)

- command တစ်ခုတည်းဖြင့် တပ်ဆင်နိုင်ပြီး ရှင်းလင်းသော တည်ဆောက်ပုံပြ မြေပုံပါဝင်သည့် ရီပိုတစ်ခု။
- ကျစ်လျစ်သော `AGENTS.md` သို့မဟုတ် ၎င်းနှင့်တူညီသည့် ရီပို လမ်းညွှန်ချက်တစ်ခု။
- ပြန်လည်အသုံးပြုနိုင်သော ကိုယ်စားလှယ် ကျွမ်းကျင်မှု (skill) တစ်ခုနှင့် MCP ပေါင်းစပ်ထည့်သွင်းမှုတစ်ခု။
- ရလဒ်သေချာသော ဟွတ် (hook) များ၊ စမ်းသပ်မှု (test) များနှင့် CI ဂိတ်များ။
- ခြိမ်းခြောက်မှုပုံစံ (threat model) တစ်ခုနှင့် အနည်းဆုံး လုပ်ပိုင်ခွင့် (least privilege) ရှိသော ခွင့်ပြုချက် (permission) ဒီဇိုင်းတစ်ခု။
- ထပ်မံကြိုးစားခြင်း (retry) များပါဝင်ပြီး ကြံ့ခိုင်မှုရှိသော၊ အစ်ရှူးမှ PR သို့သွားသည့် နောက်ကွယ်မှ (background) လုပ်ငန်းစဉ် (workflow) တစ်ခု။
- ကုန်ကျစရိတ် (cost)၊ ကြန့်ကြာချိန် (latency)၊ လမ်းကြောင်းသတ်မှတ်ပေးခြင်း (routing)၊ နှင့် ချို့ယွင်းမှုများအတွက် မော်ဒယ် (model) ဝင်ပေါက် (gateway) တယ်လီမက်ထရီ (telemetry)။
- သတ်မှတ်ထားသော အကဲဖြတ်ခြင်း (evaluation) အစုအဝေးတစ်ခုနှင့် သေးငယ်သော ရလဒ်ဒက်ရှ်ဘုတ် သို့မဟုတ် အစီရင်ခံစာတစ်ခု။
- 5 မိနစ်မှ 10 မိနစ်အထိကြာသော သရုပ်ပြသမှုတစ်ခုနှင့် ချို့ယွင်းမှုများနှင့် တိုးတက်မှုများကို ဖော်ပြထားသည့် ပြန်လည်သုံးသပ်ချက်တစ်ခု။

### မိမိဘာသာသတ်မှတ်ထားသော ပြီးစီးမှု အဆင့်များ

- အသစ် clone လုပ်ထားသည့်အရာကို မှတ်တမ်းတင်ထားသော command တစ်ခုတည်းဖြင့် တပ်ဆင်နိုင်ပြီး မှန်ကန်ကြောင်း စစ်ဆေးနိုင်ရမည်။
- အနည်းဆုံး သတ်မှတ်ထားသော အကဲဖြတ်ခြင်း အလုပ် 10 ခုတွင် အခြေခံရလဒ်နှင့် နောက်ဆုံးရလဒ်များ ရှိရမည်။
- ပြတ်တောက်သွားသော နောက်ကွယ်မှ အလုပ်တစ်ခုသည် ဆက်လက်လုပ်ဆောင်နိုင်ကြောင်း သို့မဟုတ် ရှင်းလင်းစွာ ရပ်တန့်သွားကြောင်းကို လက်တွေ့ပြသနိုင်ရမည်။
- ထုတ်ပေးလိုက်သော အပြောင်းအလဲများသည် စမ်းသပ်မှုများ၊ လုံခြုံရေး စစ်ဆေးမှုများ၊ သို့မဟုတ် လူကိုယ်တိုင် မာ့ချ် (merge) လုပ်ရန် အတည်ပြုချက်တို့ကို ကျော်လွန်သွားခွင့် မရှိရပါ။
- အလုပ်လုပ်ဆောင်မှုတိုင်းကို ၎င်း၏ အစ်ရှူး၊ စပက် (spec)၊ ပရွမ့် (prompt) များ/နောက်ခံအချက်အလက် (context)၊ ကိရိယာကို ခေါ်ယူအသုံးပြုခြင်း (tool call) များ၊ ရလဒ်များ၊ ကုန်ကျစရိတ်များနှင့် နောက်ဆုံးသုံးသပ်ချက် ဆုံးဖြတ်ချက်တို့ဆီသို့ ခြေရာခံ မှတ်တမ်းတင်ခြင်း (trace) လုပ်နိုင်ရမည်။

## အတိုချုံး စာအုပ်စင်

စာအုပ်ပေါင်းဒါဇင်များစွာကို အစအဆုံးဖတ်ရန် မကြိုးစားပါနှင့်။ ဤငါးအုပ်သည် ဤလမ်းညွှန်ချက်နောက်ကွယ်ရှိ ခိုင်မာသော အယူအဆများကို လွှမ်းခြုံထားပါသည်-

1. Chip Huyen, [*AI Engineering*](https://huyenchip.com/) — အခြေခံ မော်ဒယ် (model) များဖြင့် အက်ပ်လီကေးရှင်းများ တည်ဆောက်ခြင်းနှင့် အကဲဖြတ်ခြင်း။
2. Jay Alammar နှင့် Maarten Grootendorst, [*Hands-On Large Language Models*](https://github.com/HandsOnLLM/Hands-On-Large-Language-Models) — တွဲဖက်ပါဝင်သော ကုဒ် ရီပို (repository) နှင့်အတူ လက်တွေ့အသုံးချနိုင်သော LLM အခြေခံများ။
3. Titus Winters, Tom Manshreck, နှင့် Hyrum Wright, [*Software Engineering at Google*](https://abseil.io/resources/swe-book/html/toc.html) — အွန်လိုင်းတွင် အခမဲ့ဖတ်ရှုနိုင်ပါသည်။ အထူးသဖြင့် ကုဒ်ရီဗျူး (code review)၊ စမ်းသပ်ခြင်း (test)၊ မှီခိုမှုစီမံခန့်ခွဲခြင်းနှင့် ကြီးမားကျယ်ပြန့်သော ပြောင်းလဲမှုများအကြောင်း။
4. Adam Shostack, [*Threat Modeling: Designing for Security*](https://shostack.org/archive/2014/02/threat-modeling-designing-for-security/) — တိုက်ခိုက်ခံရနိုင်သော နေရာများတွင် ကိုယ်စားလှယ် (agent) များနှင့် ကိရိယာ (tool) များ ပါဝင်လာသည့်တိုင် အသုံးဝင်နေဆဲဖြစ်သော လုံခြုံရေးဆိုင်ရာ တွေးခေါ်မှုများ။
5. Nicole Forsgren, Jez Humble, နှင့် Gene Kim, [*Accelerate*](https://www.simonandschuster.com/books/Accelerate/Nicole-Forsgren-PhD/9781942788331) — ဆော့ဖ်ဝဲရေးသားထုတ်လုပ်ရေးစနစ်တစ်ခု တကယ်တိုးတက်လာမှု ရှိမရှိကို တိုင်းတာခြင်း။
